## Changes Made

### 1. The API container now deploys with the web container (TASK-DB-0075, #93)

- **The gap.** `deploy.sh` and `rollback.sh` ran `compose up -d --no-deps web`,
  built only `web`, and tracked only `design-bakery-web` in `.deploy-state`. The
  `api` service (added in TASK-DB-0071) was never built, started, health-checked or
  rolled back — and the `handle /api/* { reverse_proxy api:8787 }` rule already in
  the Caddyfile would 502 because nothing was listening.
- **`deploy.sh`** now, when the API is enabled: builds and tags
  `design-bakery-api:<sha12>-<utc>` (plus a bare `<sha12>`), swaps the container,
  health-checks `127.0.0.1:$API_HOST_PORT/health`, records
  `CURRENT_API_IMAGE`/`PREVIOUS_API_IMAGE` in `.deploy-state`, and rolls the API back
  with the web container when the smoke test fails.
- **`rollback.sh`** swaps the API image back alongside the web image and flips the
  API tags. A web-only rollback preserves the recorded API tags.
- **State preservation.** `api_state_current`/`api_state_previous` helpers mean a run
  that does not deploy the API never blanks the recorded API images — otherwise a
  later API-enabled rollback would find no target and silently skip the swap.
- **Enable rule** (shared by both scripts): on iff `deploy/gravebuster/.env.api`
  exists, or `WITH_API=1` in `deploy/gravebuster/.env`; `--with-api` / `--no-api`
  override for a single run. Disabled means the scripts never touch `api`. The
  decision is logged at deploy start, including the "enabled but `.env.api` missing →
  content routes will 500" warning.
- **`/api` proxy probe.** `/health` only proves the Node process is up, so a healthy
  API could still sit behind a broken Caddy rule. The deploy now GETs
  `/api/public/blogs` **through the web container**: 502/503/504 fails the deploy
  (the original bug — a routing break); a 500 only warns (a data-layer/secret
  problem, which rolling back does not fix).
- **Separate API timeout.** `API_HEALTH_TIMEOUT` defaults to 180 s, not the web's
  90 s: the API image is ~1 GB and Node cold-starts slower than Caddy.
- **Docs.** `docs/self-hosting.md` §3 (deploy steps), §4 (rollback), §7 (ports/disk/
  secrets), §8 (the API container + enable rule); `deploy/gravebuster/README.md`;
  `deploy/gravebuster/.env.example` (`API_HOST_PORT`, `DESIGN_BAKERY_API_IMAGE`,
  the `WITH_API` knob).

### 5. Open Graph link previews behind Caddy (TASK-DB-0077, issue #80 Step E)

- **The gap.** `middleware.ts` at the repo root was Vercel **Edge** middleware: it
  rewrote the SPA shell for the blog and case-study paths with crawler-friendly
  `<title>` / `og:*` tags drawn from the blog source. Nothing on gravebuster
  reproduced it, so it was the one deliberate parity gap in `docs/self-hosting.md`
  §2 — and the last code-only reason the repo still needed the Vercel project.
  Confirmed live: a crawler UA on `https://www.design-bakery.com/blogs/1` returned
  the generic homepage shell title.
- **Where it runs.** Inside the **existing** Express `api` container — no new
  sidecar, no new tunnel hostname, no DNS record, no CORS. The DOM-free OG modules
  moved to `backend/src/og/` (`blogShareHtml`, `blogSocialMeta`,
  `caseStudyShareMeta`, `linkPreviewCrawlers`, `resolveSocialPreviewImage`, plus a
  new `siteSeoDefaults`). `backend/tsconfig.json` has `rootDir: "src"`, so the
  backend cannot import from `frontend/`; the frontend therefore keeps a
  **byte-identical** copy of `blogSocialMeta.ts` and only the browser half
  (`blogSocialMetaClient.ts`) is frontend-only.
- **`backend/src/api/ogPreview.ts`** (new) is a router mounted app-wide from
  `server.ts` and is **total over the paths Caddy sends it**: blog detail (inject
  the per-post tags), blog list (list title + description), case study
  (`resolveCaseStudyShareMeta`, else the plain shell), then a catch-all shell for
  anything else matching the Caddy matcher — so a path Caddy routes here can never
  fall through to the Express 404. `next()` for everything else, and an early
  `next()` for `/\.html$/i` so a missing `.html` still 404s. Non-GET/HEAD rejected.
- **One URL, two bodies.** Every injected response sets `Vary: User-Agent` **and**
  is uncacheable (`max-age=0, must-revalidate`): Cloudflare's cache ignores
  `Vary: User-Agent`, so a shared cache would hand a crawler the browser's shell or
  vice versa. Nothing cacheable regressed — the SPA fallback already served these
  paths uncached.
- **API-down degradation.** `serveShellOrUnavailable()` sends the SPA shell with a
  real 200 when the shell fetch fails, so a web-only deploy or an API crash-loop
  cannot 502 a working blog page.
- **Caddyfile.** `@ogPreview` (`path_regexp`, identical coverage to the router) +
  `reverse_proxy api:8787`, placed **after** the filesystem handlers and the
  `.html` 404 — so a real file or a static case-study directory (study-os, fossil,
  fluffy-v4, cortex) is still served from disk and never reaches the API, and a
  missing `.html` still 404s. A top-level `handle_errors` block degrades those paths
  to the shell on dial failure; it must `respond "{file./srv/index.html}" 200`
  because `handle_errors` keeps the error's status code and `{file.}` does not
  resolve against `root`. Scoped by path so `/api/*` errors stay errors.
- **Two drift tests**, both in CI: `pnpm test:og-routing` parses the Caddy matchers
  out of the Caddyfile, evaluates the router's own regexes and checks 36 paths
  against both (they are allowed to disagree only where documented — `/blogs/abc`
  is `false` in Caddy, `shell` in Express); `pnpm test:og-contract` byte-compares
  the two `blogSocialMeta.ts` copies and compares `SITE_NAME` /
  `DEFAULT_OG_IMAGE_PATH` across the two `siteSeoDefaults.ts`.
- **Config.** `SITE_URL` on the `api` service (canonical URLs and absolute
  `og:image` links — without it the internal compose origin leaks into the tags);
  `OG_SHELL_ORIGIN` overrides the shell origin, default `http://web:80`.
  `scripts/find-orphans.mjs`'s `EXTRA_ENTRIES` is now empty — `middleware.ts` was
  the only entry.

### 6. The live build now reads octo (TASK-DB-0078)

- **The gap.** The cutover (TASK-DB-0076) moved the domain but left
  `deploy/gravebuster/.env` with no `VITE_BLOG_API_URL`. `VITE_*` is inlined at
  **build** time, so the deployed SPA never called the backend: `/blogs` rendered
  "6 of 7 posts" from the committed
  `frontend/src/app/modules/blog/data/blog-data.json` snapshot while octo had **33**,
  and `sitemap.xml` listed only 14 blog URLs (the snapshot's). On Vercel this was
  configured; the cutover dropped it.
- **The fix.** `VITE_BLOG_API_URL=https://www.design-bakery.com` in the box's
  `deploy/gravebuster/.env`, then a rebuild (a build arg, not a restart). The site's
  own origin keeps the browser **same-origin** with Caddy's `/api/*` proxy (no CORS,
  no `ALLOWED_ORIGINS` change) and — being an absolute URL, not the literal
  `same-origin` — is also reachable by the **build-time sitemap generator**
  (`scripts/generate-sitemap.mjs`), which has no browser origin. `same-origin` fixes
  the page but not the sitemap, which is why the absolute origin was chosen.
- **Verified live** (same SHA, redeployed with the env): `/blogs` → "6 of 33 posts"
  with `GET /api/public/blogs` + `GET /api/public/blog-categories` **same-origin**;
  `/blogs/23` → the post title and body from `GET /api/public/blogs/23`;
  `sitemap.xml` → **66** blog URLs (was 14). Nothing in `frontend/` changed —
  `resolveApiBase` already accepted an absolute URL, and
  `isSupabaseDirectReadEnabled()` stays false while `VITE_BLOG_API_URL` is set, so the
  octo backend is authoritative and the legacy Supabase anon-key read stays off.
- **Watch for this class of gap:** every build-time `VITE_*` the Vercel project had
  must be re-set on the box, or the build silently degrades to its committed fallback.

### 7. The `/srv` hosting-convention target (TASK-DB-0079, issue #98)

- Issue [#98](https://github.com/Pukujan/design-bakery/issues/98) asks each hosted
  project to conform to the operator's one-project-one-directory standard and is
  explicit that it **authorizes no server change by itself**. TASK-DB-0079 did the
  authoring and validation half only; the move is owner-gated.
- **`deploy/gravebuster/PROJECT.json`** (new) — the manifest the standard calls for
  (owner, purpose, exposure, data, compose). The schema is **inferred** from the issue,
  which names the fields but gives no spec; reconcile it against a sibling project's
  before treating it as canonical.
- **The api port default was wrong.** The compose default, both scripts' fallback,
  `.env.example` and the docs all said `8788`, but `ss -tlnp` shows `8788` is held by
  another stack on gravebuster (`rootlessport`) — which is why the box's `.env` sets
  `API_HOST_PORT=8789`. A fresh box without that override would have failed to bind.
  All four defaults now read `8789`.
- **The move is blocked, and not by "two edits and a move".** The target puts the repo
  at `/srv/design-bakery/app/` with the deploy files at `/srv/design-bakery/`, but both
  `deploy.sh`/`rollback.sh`
  (`REPO_DIR=${DEPLOY_REPO_DIR:-$(cd "$SCRIPT_DIR/../.." && pwd)}`) and the compose
  build context (`../..`) derive the repo from their own location — from
  `/srv/design-bakery/` those resolve to `/`, not the repo. So the scripts and compose
  need parameterizing **before** the move; that is a code change belonging with the
  cutover, deliberately not made here.
- **Read-only validation** confirmed the current stack already conforms where it counts:
  both containers bind `127.0.0.1` only, the compose file pins `name: design-bakery`,
  and the `docker-compose.edge.yml` overlay exists. The box also has two untracked
  `.env.bak*` **backups** (`git stash list` is empty) — an owner cleanup decision, not
  unpushed work.

### 8. The IRE dashboard becomes the `/ire` page, and auto-deploy goes live (TASK-DB-0081)

Two owner decisions closed together, because the second one is only safe once the first
has a way to ship.

- **The dashboard moved to the canonical path.** TASK-DB-0080 shipped the React
  dashboard at `/ire/app/` and left the static page owning `/ire`; the owner chose
  `/ire/`. `frontend/ire-app/vite.config.ts` builds with `base: "/ire/"`,
  `src/App.tsx` carries `basename="/ire"`, and `scripts/build-ire-app.mjs` copies the
  output to `frontend/dist/ire`. `/ire/app` and `/ire/app/` now 301 to `/ire/` in both
  `vercel.json` (a `redirects` entry, `permanent: true`) and the Caddyfile
  (`redir @ireAppLegacy /ire/ 301`).
- **Retiring the static page was not a deletion.** With `frontend/public/ire/index.html`
  gone, no crawler or link unfurler sees any markup — the app renders its own DOM in the
  browser. So the static page's whole head moved into `frontend/ire-app/index.html`:
  title, description, robots, canonical, `theme-color`, the `og:*` and `twitter:*` sets,
  and the JSON-LD `@graph` (a `WebPage` about a `Dataset` whose distribution is the live
  feed). What a non-JS crawler gets is now the app shell's head, which is the same head
  the static page served.
- **`IrePageRedirect` stays.** The portfolio card renders `/ire` as a react-router
  `<Link>`, so the handoff is client-side and no host rewrite runs. The stub now warns
  and does nothing under `import.meta.env.DEV`, because the site's dev server has no
  `/ire` proxy and the redirect would loop.
- **The og-image card is its own asset.** `frontend/ire-app/public/og-image.png` is a
  dark brand card, not a screenshot of the light dashboard, and its source
  (`scripts/ire-og-image/og-image.html`) used to link the retired `theme.css`. The tokens
  it actually used are inlined in that file now; the committed PNG is byte-identical, so
  it was not regenerated.
- **The lock.** `deploy.sh` and `rollback.sh` take `exec 9>"$LOCK_FILE"` +
  `flock -n 9 || die …` as their first action after the environment guards.
  `deploy/gravebuster/.deploy.lock` is git-ignored and `DEPLOY_LOCK_FILE` overrides the
  path. Non-blocking on purpose: the loser fails fast, and the timer retries five minutes
  later rather than queueing behind a deploy that can take thirty.
- **The timer.** `design-bakery-autodeploy.{service,timer}` were copied to
  `/etc/systemd/system/` and `systemctl enable --now design-bakery-autodeploy.timer` was
  run. Issue #52's last unmet "Done when" — *merging to main deploys automatically* — is
  met. The lock ships in the same change, so the timer was never live without it.
