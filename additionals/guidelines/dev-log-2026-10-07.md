## Changes Made

### 1. The API container now deploys with the web container (TASK-DB-0075, #93)

- **The gap.** `deploy.sh` and `rollback.sh` ran `compose up -d --no-deps web`,
  built only `web`, and tracked only `design-bakery-web` in `.deploy-state`. The
  `api` service (added in TASK-DB-0071) was never built, started, health-checked or
  rolled back — and the `handle /api/* { reverse_proxy api:8787 }` rule already in
  the Caddyfile would 502 because nothing was listening.
- **`deploy.sh`** now, when the API is enabled: builds and tags
  `design-bakery-api:<sha12>-<utc>` (plus a bare `<sha12>`), swaps the container,
  health-checks `127.0.0.1:$API_HOST_PORT/health`, records
  `CURRENT_API_IMAGE`/`PREVIOUS_API_IMAGE` in `.deploy-state`, and rolls the API back
  with the web container when the smoke test fails.
- **`rollback.sh`** swaps the API image back alongside the web image and flips the
  API tags. A web-only rollback preserves the recorded API tags.
- **State preservation.** `api_state_current`/`api_state_previous` helpers mean a run
  that does not deploy the API never blanks the recorded API images — otherwise a
  later API-enabled rollback would find no target and silently skip the swap.
- **Enable rule** (shared by both scripts): on iff `deploy/gravebuster/.env.api`
  exists, or `WITH_API=1` in `deploy/gravebuster/.env`; `--with-api` / `--no-api`
  override for a single run. Disabled means the scripts never touch `api`. The
  decision is logged at deploy start, including the "enabled but `.env.api` missing →
  content routes will 500" warning.
- **`/api` proxy probe.** `/health` only proves the Node process is up, so a healthy
  API could still sit behind a broken Caddy rule. The deploy now GETs
  `/api/public/blogs` **through the web container**: 502/503/504 fails the deploy
  (the original bug — a routing break); a 500 only warns (a data-layer/secret
  problem, which rolling back does not fix).
- **Separate API timeout.** `API_HEALTH_TIMEOUT` defaults to 180 s, not the web's
  90 s: the API image is ~1 GB and Node cold-starts slower than Caddy.
- **Docs.** `docs/self-hosting.md` §3 (deploy steps), §4 (rollback), §7 (ports/disk/
  secrets), §8 (the API container + enable rule); `deploy/gravebuster/README.md`;
  `deploy/gravebuster/.env.example` (`API_HOST_PORT`, `DESIGN_BAKERY_API_IMAGE`,
  the `WITH_API` knob).

### 5. Open Graph link previews behind Caddy (TASK-DB-0077, issue #80 Step E)

- **The gap.** `middleware.ts` at the repo root was Vercel **Edge** middleware: it
  rewrote the SPA shell for the blog and case-study paths with crawler-friendly
  `<title>` / `og:*` tags drawn from the blog source. Nothing on gravebuster
  reproduced it, so it was the one deliberate parity gap in `docs/self-hosting.md`
  §2 — and the last code-only reason the repo still needed the Vercel project.
  Confirmed live: a crawler UA on `https://www.design-bakery.com/blogs/1` returned
  the generic homepage shell title.
- **Where it runs.** Inside the **existing** Express `api` container — no new
  sidecar, no new tunnel hostname, no DNS record, no CORS. The DOM-free OG modules
  moved to `backend/src/og/` (`blogShareHtml`, `blogSocialMeta`,
  `caseStudyShareMeta`, `linkPreviewCrawlers`, `resolveSocialPreviewImage`, plus a
  new `siteSeoDefaults`). `backend/tsconfig.json` has `rootDir: "src"`, so the
  backend cannot import from `frontend/`; the frontend therefore keeps a
  **byte-identical** copy of `blogSocialMeta.ts` and only the browser half
  (`blogSocialMetaClient.ts`) is frontend-only.
- **`backend/src/api/ogPreview.ts`** (new) is a router mounted app-wide from
  `server.ts` and is **total over the paths Caddy sends it**: blog detail (inject
  the per-post tags), blog list (list title + description), case study
  (`resolveCaseStudyShareMeta`, else the plain shell), then a catch-all shell for
  anything else matching the Caddy matcher — so a path Caddy routes here can never
  fall through to the Express 404. `next()` for everything else, and an early
  `next()` for `/\.html$/i` so a missing `.html` still 404s. Non-GET/HEAD rejected.
- **One URL, two bodies.** Every injected response sets `Vary: User-Agent` **and**
  is uncacheable (`max-age=0, must-revalidate`): Cloudflare's cache ignores
  `Vary: User-Agent`, so a shared cache would hand a crawler the browser's shell or
  vice versa. Nothing cacheable regressed — the SPA fallback already served these
  paths uncached.
- **API-down degradation.** `serveShellOrUnavailable()` sends the SPA shell with a
  real 200 when the shell fetch fails, so a web-only deploy or an API crash-loop
  cannot 502 a working blog page.
- **Caddyfile.** `@ogPreview` (`path_regexp`, identical coverage to the router) +
  `reverse_proxy api:8787`, placed **after** the filesystem handlers and the
  `.html` 404 — so a real file or a static case-study directory (study-os, fossil,
  fluffy-v4, cortex) is still served from disk and never reaches the API, and a
  missing `.html` still 404s. A top-level `handle_errors` block degrades those paths
  to the shell on dial failure; it must `respond "{file./srv/index.html}" 200`
  because `handle_errors` keeps the error's status code and `{file.}` does not
  resolve against `root`. Scoped by path so `/api/*` errors stay errors.
- **Two drift tests**, both in CI: `pnpm test:og-routing` parses the Caddy matchers
  out of the Caddyfile, evaluates the router's own regexes and checks 36 paths
  against both (they are allowed to disagree only where documented — `/blogs/abc`
  is `false` in Caddy, `shell` in Express); `pnpm test:og-contract` byte-compares
  the two `blogSocialMeta.ts` copies and compares `SITE_NAME` /
  `DEFAULT_OG_IMAGE_PATH` across the two `siteSeoDefaults.ts`.
- **Config.** `SITE_URL` on the `api` service (canonical URLs and absolute
  `og:image` links — without it the internal compose origin leaks into the tags);
  `OG_SHELL_ORIGIN` overrides the shell origin, default `http://web:80`.
  `scripts/find-orphans.mjs`'s `EXTRA_ENTRIES` is now empty — `middleware.ts` was
  the only entry.
