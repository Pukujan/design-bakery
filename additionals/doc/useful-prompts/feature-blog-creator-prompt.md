# Feature blog creator prompt (v1)

Reusable prompt for drafting a **feature-focused engineering blog post** in my style. Use this when I want to explain a feature, package, module, tool, workflow, or architecture I built.

## Prompt template

I want you to write a well-structured Markdown feature blog in my style.

Use this style:
- Direct, personal, practical, and fun
- Chill but useful
- Aesthetic builder-energy
- Clear "problem → solution → how it works → why it matters" flow
- Make it feel like I am showing something I actually built
- Light “let’s go” energy, but not cringe
- Not too salesy
- Not too formal
- Not too conclusive or preachy
- Use simple language
- Make it skimmable
- Use headings, short paragraphs, tables, Mermaid diagrams, and code blocks where useful
- Avoid unnecessary theory unless it explains the feature
- No em dashes

Brand voice rules:
- Make it feel fun, aesthetic, and builder-energy
- Light “let’s go” energy is good
- Use casual phrases naturally, but do not overdo it
- Sound excited, not cringe
- Sound confident, not salesy
- Keep the writing clean and useful
- Use phrases like:
  - “let’s go”
  - “this is where it clicked”
  - “this was the messy part”
  - “the fun part”
  - “tiny win”
  - “builder brain moment”
  - “now this feels reusable”
  - “this is why I like this pattern”
  - “not perfect yet, but much cleaner”
- Avoid sounding like marketing copy
- Avoid fake hype
- Avoid too many emojis
- Avoid motivational-influencer tone

Formatting rules:
- Start with a clear title
- Add a short intro
- Add a Table of Contents
- Use sections with clear headings
- Include practical examples
- Include a "before vs after" table when useful
- Include "problems I ran into / how I handled them" if useful
- Include a simple "how it works" section
- Include a short takeaway near the end
- Keep the ending open-ended, like I am still improving the tool

Mermaid chart rules:
- Use Mermaid charts where they help explain the workflow or architecture visually
- Prefer vertical top-to-bottom charts
- Do not make giant unreadable charts
- Break complex ideas into 2 or 3 smaller charts instead of one huge chart
- Use readable labels
- Make charts useful, not decorative

My preferred story flow:
1. What I built: briefly introduce the feature, package, or workflow
2. Why I needed it: explain the real problem or friction that made me build it
3. The messy version before: show what was difficult, slow, confusing, or risky
4. The feature: explain the solution in simple terms
5. How it works: show the workflow, architecture, or command flow
6. Before vs after: make the improvement concrete
7. Problems I ran into: mention challenges, tradeoffs, or things I had to clean up
8. How someone else can use it: give a simple copy-paste example or usage flow
9. Why this matters: explain the practical value without overhyping it
10. Open-ended takeaway: end with what I am still testing, improving, or learning

Important:
- Do not add unrelated advice
- Do not expand into a different topic
- Keep the blog focused on the feature I am trying to document
- Make it practical and useful for people who want to understand or try it
- Do not make it sound like a startup pitch
- Make it sound like a builder explaining what they made and why
