# Black-box and grey-box validation of autonomous agent work

> **Provenance note.** This is a technical survey and position paper. It reports no original benchmark experiment or production deployment; all quantitative findings are attributed to prior publications. References and numerical claims must be independently verified before owner approval. Citations were AI-suggested; several carry 2026 arXiv identifiers that must be confirmed before this paper is marked `approved`.

## Abstract

AI agents are difficult to evaluate because their behaviour emerges from multi-turn interaction, tool use, external state, retrieval, memory, orchestration, and probabilistic model outputs. Evaluating only the final answer can miss unsafe or defective execution paths, while evaluating internal traces can over-constrain valid implementations or create a circular system in which the agent, evaluator, trace generator, and acceptance criteria all share the same assumptions. This paper distinguishes *black-box* validation, which evaluates externally observable behaviour without depending on internal implementation, from *grey-box* validation, which evaluates selected internal information such as tool trajectories, intermediate states, coverage, policy decisions, and execution traces. The two provide complementary evidence but cannot validate one another automatically. The central conclusion is that black-box and grey-box validation should be treated as independent evidence channels whose oracles, instrumentation, and failure modes must themselves be tested.

## 1. Introduction

A conventional software function can often be evaluated by providing an input and comparing the output against an expected value. AI agents are more complicated: an agent may hold a multi-turn conversation, retrieve external information, invoke tools, modify files or databases, delegate to other models, maintain memory, recover from failed actions, make nondeterministic decisions, and produce an apparently correct outcome through an incorrect process. A useful evaluation method must therefore answer at least two distinct questions: (1) did the agent produce the correct externally observable result, and (2) did it reach that result through an acceptable execution process? Black-box validation primarily addresses the first; grey-box validation primarily addresses the second, though the boundary is not absolute. The software-testing literature calls the difficulty of determining whether a result is correct the *test-oracle problem*: even when execution is fully observable, the evaluator may lack a complete or reliable definition of correct behaviour [1]. For agents this is more severe, since natural-language requirements may be ambiguous, several outputs may be acceptable, environments change, and an evaluator model may share the agent's misconceptions.

## 2. Definitions

### 2.1 Black-box validation

Black-box validation evaluates a system through its externally observable interface without relying on internal implementation. The validator may observe user inputs, final responses, externally visible tool effects, database or filesystem state, public errors and status codes, timing and resource consumption, and whether the requested task was completed. It ordinarily does not depend on internal prompts, source code, hidden reasoning, intermediate plans, internal memory, model-provider identity, or private tool-selection logic.

```
Initial environment state + User request
 ↓
Agent system
 ↓
Final response and external state
 ↓
Outcome oracle
```

For example, an airline-support agent instructed to cancel an eligible reservation can be judged on whether the reservation was actually cancelled, whether correct fees were applied, and whether unrelated reservations were left unchanged. Recent research introduced AgentEval, a black-box framework that mines conversational workflow graphs from observed interactions, replays paths to important boundaries (confirmation, identity checks), and perturbs the interaction there. On four τ³-bench agents it covered between 23 and 38 distinct boundaries per agent, compared with 12 for a prompt-only baseline [2], evidence that structured black-box exploration can reveal state-dependent failures without source access, though not that it enumerates every state.

### 2.2 Grey-box validation

Grey-box validation examines externally observable behaviour while also using selected internal information, sequences of tool calls, tool arguments, intermediate states, retrieval results, execution spans, code and branch coverage, policy decisions, memory reads and writes, latency by stage, generated plans, sandbox events, and intermediate task progress.

```
Initial environment state + User request
 ↓
Agent system
 ├── final response
 ├── tool trajectory
 ├── intermediate states
 ├── execution metadata
 └── selected instrumentation
 ↓
Outcome oracle + process oracle
```

The term is well established in software testing, especially coverage-guided fuzzing, where fuzzers observe limited execution feedback (newly reached control-flow paths) to guide test generation without full semantic analysis [3]. AgentBoard is a trajectory-aware evaluation framework that supplements final success rates with progress rates, grounding accuracy, subskill analysis, long-range interaction measurements, and trajectory visualisation; its progress metrics correlated above 0.95 with human progress assessments on the evaluated tasks [4]. In this paper, grey-box means any evaluation that uses selected internal execution evidence in addition to final observable outcomes.

### 2.3 White-box validation

White-box validation has broad access to implementation details, complete source, system and developer prompts, orchestration logic, policy definitions, memory implementation, model configurations, and test-generation code. It can identify structural vulnerabilities and unreachable branches but is more tightly coupled to the implementation, and it risks validating what the system claims to do rather than what the deployed system actually does. This paper treats white-box analysis as a complementary engineering and auditing method and focuses on black-box and grey-box approaches.

## 3. The case for black-box validation

**3.1 Implementation independence.** A black-box test can remain valid when the implementation changes. "The agent must not issue a refund without the required approval" can be tested regardless of model provider, prompt structure, orchestration framework, number of subagents, language, or internal authorization implementation, useful for comparing architectures under the same observable requirements.

**3.2 End-to-end evaluation.** Black-box testing includes failures caused by interactions between components: a correct tool and arguments can still fail because an adapter transforms an argument, the environment is in an unexpected state, a call is retried, the final response claims a success that did not occur, or a later step reverses an earlier correct action. τ-bench compares the final database state against an annotated goal state and introduced "pass^k", measuring whether an agent succeeds consistently across repeated executions rather than once by chance [5].

**3.3 Resistance to implementation-specific gaming.** When the evaluator does not expose its expected trajectory, the agent cannot pass merely by emitting expected trace labels, though it may still overfit to public task distributions, recognisable benchmark wording, or repeatedly queried hidden evaluations.

## 4. Strict critique of black-box validation

**4.1 The oracle can be wrong.** A black-box test is only as reliable as its expected outcome. Repairing a defect and checking that supplied tests pass misses a patch that breaks behaviour those tests do not cover. An empirical analysis of SWE-bench Verified found that 7.8% of patches counted as correct nevertheless failed developer-written tests. Differential testing found behavioural discrepancies in 29.6% of plausible patches, and the combined weaknesses inflated reported resolution rates by 6.2 absolute percentage points [6].

**4.2 Correct outcome, incorrect cause.** A result may be correct accidentally, no unauthorized transfer happens because the payment service crashed, not because authorization worked.

**4.3 Limited diagnosis.** A black-box failure can show that a system is wrong without showing why.

**4.4 Sparse coverage.** A passing sample does not prove nearby or hidden behaviours are correct; state-dependent boundaries may require specific earlier actions to become reachable [2].

**4.5 Nondeterministic success.** Sampling, latency, retrieval variation, or race conditions can make one run pass and another fail; single-run accuracy overestimates reliability, which "pass^k" exposes [5].

**4.6 Public benchmark contamination.** Public benchmarks expose tasks and sometimes solutions; a high score can measure benchmark familiarity, which continuously refreshed benchmarks such as SWE-bench-Live aim to reduce [7].

## 5. The case for grey-box validation

**5.1 Diagnosing where failure occurred.** A trace separates a wrong result into: the correct tool was never called; the wrong tool was selected; the right tool received incorrect arguments; the tool succeeded but the agent misread the result; the environment changed after execution.

**5.2 Detecting accidental success.** An agent may complete a transaction but perform unnecessary privileged calls, retry a non-idempotent operation, read unrelated confidential records, ignore a required confirmation, or reach the correct state through an unsafe shortcut; a final-state oracle marks it successful while a trajectory evaluator catches the violation.

**5.3 Measuring partial progress.** Final success is too coarse for long-horizon tasks; AgentBoard's progress-rate methodology captures incremental advancement and distinguishes systems with similar low final success but different partial capabilities [4].

**5.4 Coverage-guided test generation.** Coverage-guided fuzzers prioritise inputs reaching new paths; FuzzBench compares fuzzers reproducibly and Magma supplements coverage with known ground-truth bugs [8, 9], an agent analogue could guide generation using unexplored tool sequences, unvisited states, or untested policy branches.

**5.5 Efficiency and cost analysis.** Trajectory evidence measures tool calls, unnecessary retries, model-call count, tokens, latency, and progress per step; OSWorld-Human found even high-scoring computer-use agents often took far more steps than necessary [10].

## 6. Strict critique of grey-box validation

**6.1 Instrumentation is not ground truth.** A trace is an observation produced by an instrumentation system, not a complete record of reality; it may omit direct network calls, writes by another process, delayed side effects, out-of-band communication, or events after trace completion. If the agent generates its own authoritative trace, it may emit a convincing but false account; grey-box evidence should be corroborated against independently observed state.

**6.2 The trajectory-equivalence problem.** Multiple valid trajectories may produce the same correct result; comparing against one "golden trajectory" incorrectly rejects valid alternatives. The process oracle should specify invariants and forbidden actions, "user identity verified before write; no unrelated records accessed; exactly one successful payment", not require exact imitation of a reference trace.

**6.3 Overfitting to the evaluator.** Detailed trajectory feedback invites optimising for the visible evaluator rather than general behaviour.

**6.4 Implementation coupling.** Grey-box tests depend on trace schemas, tool names, and internal structure; a refactor may break them even when external behaviour is unchanged.

**6.5 Instrumentation can alter behaviour.** Tracing affects timing, concurrency, memory, and prompt context, an observer effect.

**6.6 Exposure of sensitive information.** Traces may contain user data, credentials, and file contents; trace access should be treated as privileged.

## 7. Circular validation

Circular validation occurs when the system being evaluated and the system determining correctness share the same assumptions, models, data, or artifacts:

```
Model creates answer → Related model evaluates answer →
Evaluation confirms shared assumptions → Result treated as independent validation
```

Adding more evaluators does not eliminate circularity when they share the same error source.

**7.2 Shared-oracle circularity.** An incorrect requirement can feed the black-box expected result, the grey-box required trajectory, the judge rubric, and the human checklist alike; all layers agree while validating the wrong behaviour [1].

**7.3 LLM-as-judge bias.** The MT-Bench study found strong agreement between capable LLM judges and human preferences but also position bias, verbosity bias, self-enhancement bias, and reasoning limits [11]; self-preference research found judges may favour outputs more familiar to their own distribution (lower-perplexity outputs) rather than objectively better ones [12], a different vendor helps but does not make the evaluator independent. **7.4 Correlated model errors.** A study of more than 350 models found substantial correlation between model errors, including across families and providers [13]; consensus measures agreement, not truth. **7.5 Adaptive holdout overfitting.** A hidden set becomes effectively visible through repeated interaction; adaptive-data-analysis research showed repeated holdout consultation causes overfitting even when the examples are never disclosed [14].

**7.6 Benchmark gaming.** A public, important benchmark becomes a development target; ordinary iterative improvement gradually specialises a system to it.

**7.7 Trace circularity.** A grey-box evaluator becomes circular when it trusts execution records generated by the component it is evaluating; the trace should come from independent instrumentation or the environment.

## 8. Anti-circular validation design

1. **Separate outcome and process oracles.** The process evaluator must not reinterpret an incorrect external outcome as successful; the outcome evaluator must not ignore a critical process violation.
2. **Prefer deterministic evidence**, database/filesystem state, JSON structure, call arguments, compiler results, unit tests, access-control decisions, schema compliance, forbidden operations. Use model judges only for semantic questions that cannot be reduced to deterministic checks.
3. **Evaluate invariants, not exact trajectories.** Distinguish required invariants (permitted order, required confirmation, no sensitive-data access, no duplicate write) from optional implementation choices (exact wording, reasoning sequence, harmless extra retrieval).
4. **Independently observe final state.** Query the system of record. If the agent claims "reservation cancelled" but the database shows it active → FAIL.
5. **Blind model judges**, conceal producer identity, randomise and reverse answer ordering, remove stylistic metadata, commit initial judgments before showing others' opinions, calibrate against labelled examples.
6. **Limit hidden-evaluation feedback.** Visible development set with diagnostics; a diagnostic holdout with limited queries and broad categories; a final holdout of fresh or rarely reused cases with minimal feedback. Count every query to a protected holdout.
7. **Use metamorphic and differential testing**, reordering irrelevant records should not change the decision; removing required approval should flip allow→deny; two implementations should agree on shared requirements.
8. **Test the evaluator.** Challenge every validation component with deliberately defective cases: a superficially successful but incomplete result; an alternate valid trajectory; an intentionally unlogged side effect; reversed candidate order with concealed authorship; repeated-query inference; known scoring mistakes; seeded defects; delayed and duplicated events. An evaluator never tested against known failures should not be treated as authoritative.

## 9. Publicly available benchmarks

*Operational classification; many benchmarks run black-box while also collecting traces for grey-box analysis.*

- **τ-bench / τ³-bench**, conversational tool-using agents under domain policies; black-box final-state comparison plus "pass^k"; simulated users may not represent production [5].
- **AgentBoard**, analytical, strong grey-box/progress elements; annotations may privilege expected solution structures [4].
- **AgentBench**, LLMs as agents across eight interactive environments; aggregate scores can hide per-domain differences [15].
- **SWE-bench**, coding agents on real GitHub issues; black-box execution via repository tests; the supplied oracle may be incomplete [6].
- **WebArena**, autonomous web interaction in self-hosted environments; multiple valid paths; environment maintenance needed for reproducibility [16].
- **OSWorld / OSWorld 2.0**, multimodal computer-use agents on real desktops (369 tasks; 2.0 adds 108 longer workflows); a correct final state does not establish the intended/safest method [17, 18].
- **BFCL**, function selection and argument generation via AST and executable validation; measures the function-calling layer, not full agent safety [19].
- **AgentDojo**, utility and security under indirect prompt injection; static attacks can become development targets [20].
- **Agent Security Bench**, attacks and defences across agent stages; threat models cannot cover unknown attacks or all tool compositions [21].
- **AgentDyn**, dynamic open-ended prompt-injection (60 tasks, 560 injections); still a finite curated benchmark [22].
- **FuzzBench**, reproducible coverage-guided fuzzer comparison; coverage is an imperfect proxy for defect detection [8].
- **Magma**, fuzzers against known ground-truth bugs; shows internal metrics like coverage should be validated against meaningful ground-truth failures [9].

## 10. Production and open-source evaluation tools

These operationalise black-box and grey-box evaluation but do not prove the evaluation design is non-circular.

- **Inspect AI** (UK AI Security Institute), tasks, tool agents, custom/model-graded scorers, sandbox execution, logs/traces; Inspect Evals ships 200+ evaluations including SWE-bench. Provides machinery, not guarantees of scorer correctness, holdout independence, judge neutrality, trace completeness, or benchmark-to-production match [23].
- **LangSmith**, offline datasets, final-response and trajectory evaluators, model judges, production tracing; trajectory evaluation may depend on judges or reference trajectories; users design their own independence and anti-overfitting controls [24].
- **Braintrust**, datasets, code/LLM/trace-level scorers, online production scoring; quality depends heavily on customer-created scorers and datasets [25].
- **Arize Phoenix**, OpenTelemetry-based observability plus evaluation across model calls, retrieval, and tools; observability is not validation, a complete-looking trace may omit uninstrumented effects, and a high score may rely on a weak oracle [26].

No surveyed production tool proves that combining black-box and grey-box testing eliminates circular validation. The user must still determine who creates the oracle, whether it is independent, whether traces are trustworthy, whether hidden evaluations are protected, whether judges are calibrated, whether test cases represent production, whether evaluators have correlated errors, and whether the evaluator itself has been adversarially tested.

## 11. Recommended evaluation protocol

- **Layer A, black-box outcome:** final task completion, external state, unintended side effects, consistency across repeated runs, performance under perturbed inputs. Never rely solely on the agent's verbal success claim.
- **Layer B, grey-box invariants:** required steps, forbidden actions, tool correctness, sensitive-data access, duplication/retries, progress, resource consumption. Avoid requiring exact reference trajectories unless only one is truly valid.
- **Layer C, evaluator validation:** scoring implementation, trace completeness, judge ordering bias, judge self-preference, benchmark contamination, holdout leakage, alternative valid strategies, known defective behaviours.
- **Layer D, production validation:** sampled production traces, independently observed outcomes, human incident review, new regression cases from failures, periodically refreshed benchmarks, distribution-shift monitoring.

```
PASS = external outcome correct
 AND critical process invariants satisfied
 AND evaluation infrastructure healthy
 AND repeated-run reliability acceptable
```

Model consensus must not override a deterministic external-state failure or a critical invariant violation.

## 12. Proposed empirical evaluation

This paper is a position paper, not an experiment. The clearest way to turn it into an experimental contribution is to measure the incremental value of each evaluation channel directly: run the same set of agents under four evaluator conditions and compare what each detects.

- **A, black-box only:** an outcome oracle over external state.
- **B, grey-box only:** a process oracle over invariants and trajectory.
- **C, combined:** independently generated black-box and grey-box evidence.
- **D, combined with evaluator fault injection:** condition C while deliberately corrupting the evaluators, to measure robustness of the combination itself.

Across the conditions, inject known failure classes so the ground truth is controlled:

- a correct outcome caused by a crash or an unsafe shortcut;
- a correct trace but a wrong external result;
- a forged or incomplete trace;
- an alternate valid trajectory;
- an unauthorized intermediate access;
- a duplicate non-idempotent tool call;
- a delayed side effect;
- evaluator position bias;
- repeated hidden-set feedback;
- benchmark-specific overfitting.

Measure, per condition: false-acceptance rate; false-rejection rate; critical-defect recall; time to diagnosis; evaluation cost; sensitivity to alternative valid trajectories; trace-omission detection; repeated-run reliability; and evaluator-bias rate. The experiment tests the paper's central proposition:

> Does combining independently generated black-box and grey-box evidence detect more meaningful failures than either method alone, without producing unacceptable false rejection or cost?

## 13. Conclusions

Black-box validation asks "did the agent produce the correct observable outcome?"; grey-box validation asks "what happened during execution, and were required process properties preserved?" Black-box is more implementation-independent and better aligned with user-visible results but suffers from incomplete oracles, sparse coverage, weak diagnosis, nondeterminism, and benchmark gaming. Grey-box provides process visibility, diagnosis, coverage feedback, partial-progress measurement, and detection of accidental success but can trust incomplete instrumentation, reject valid alternate strategies, couple tests to implementation, expose sensitive information, and encourage optimisation for the evaluator. Combining both is stronger than either alone, but the combination does not automatically solve circularity. The correct claim is not "black-box and grey-box validation prove that an agent is correct," but "together they create complementary evidence about outcomes and execution processes, provided that their oracles, instrumentation, benchmarks, and evaluators are themselves independently challenged."
