# Neuro-Symbolic Control for Reliable Multi-Model Coding Agents

## Deterministic Safety Gates, Learned Harness Policies, Verifier Rewards, and Vendor-Neutral Model Allocation

### Position, Architecture, and Experimental Methods Paper

## Abstract

Current coding agents commonly place a large language model at the center of planning, tool selection, implementation, verification, model routing, and termination. This creates a structural reliability problem: the same probabilistic model may generate work, interpret feedback, decide whether the work is correct, select which other model to trust, and determine whether execution should continue.

This paper proposes a hybrid architecture in which these responsibilities are divided among three layers:

1. a deterministic safety and workflow kernel;
2. a locally trained neural control model;
3. one or more frontier language models acting as code-generating workers.

The deterministic layer owns permissions, workflow state, budgets, artifact identity, irreversible effects, and non-compensatory safety constraints. The neural controller learns bounded structural decisions such as which model to invoke, whether to test or revise, when to escalate, and whether additional work is likely to improve the result. Frontier language models generate code, critiques, plans, and natural-language explanations but do not control authoritative workflow transitions.

The proposed architecture is motivated by recent work showing that an agent harness can itself be learned while the underlying LLM remains frozen; that learned routers can select among multiple language models; and that learned reward or verifier models can improve code generation and software-engineering agents. At the same time, research on reward overoptimization, reward tampering, and verification limitations shows that learned rewards cannot safely replace deterministic checks or external evidence.

We call the proposed system a **Neuro-Symbolic Coding Control Plane**, or NSCCP. Its central principle is:

> The neural controller may optimize execution within a mechanically safe region, but it may not redefine that region.

This paper presents the architecture, training data format, reward design, model-allocation strategy, deployment procedure, experimental protocol, and strict failure analysis. It reports no original experimental results.

# 1. Introduction

A modern coding agent is more than a language model receiving a prompt. Its surrounding harness determines when the model:

* reads repository state;
* performs research;
* edits files;
* runs tests;
* invokes another model;
* requests review;
* revises a patch;
* stops execution;
* submits or merges work.

Recent research has formalized the harness itself as a learnable control layer. Yi and Song define a finite-horizon Harness Markov decision process in which a lightweight controller chooses structural actions, including observation, retrieval, tool calls, drafting, checking, revision, and submission, while the underlying LLM remains frozen. Their offline reinforcement-learning experiments reported improvements in verification behavior and selective improvements in task quality across controlled domains and public-benchmark adapters. This is recent preprint evidence rather than an established production result, but it directly supports the idea that the control process around an LLM can be learned independently from the LLM. [1]

Learned model routing is also established as a research direction. RouteLLM trains routers from preference data to choose between stronger and weaker models, while RouterBench and later LLMRouterBench provide large datasets and frameworks for evaluating multi-model routing. These studies support the premise that different models have complementary strengths and that a learned allocator can improve cost-performance trade-offs. They also reveal a substantial gap between learned routers and an ideal oracle, meaning that model allocation remains an imperfect prediction problem. [2–4]

Coding-specific reward and verifier models provide a third foundation. SWE-RM trains a learned reward model for software-engineering trajectories and reports improvements in both test-time selection and reinforcement learning on SWE-bench Verified. Related work trains process reward models or active test-generating verifiers to distinguish correct and incorrect code candidates. These results show that learned models can provide useful intermediate supervision, but they do not establish that learned verification can safely replace execution or formal checks. [5–7]

The central question of this paper is:

> Can a coding engine combine deterministic gates, a mechanical reward process, and a locally trained neural controller so that frontier language models perform work more reliably without becoming the root of trust?

The proposed answer is yes, with a crucial limitation:

> The local neural network may guide and prioritize work, but deterministic infrastructure must retain final control over permission, evidence, and irreversible effects.

# 2. Relationship to a Neural Personality Engine

A personality system may separate:

```text
latent internal state
→ behavioral and emotional policy
→ language model verbalization
```

The language model acts as an expressive speaker rather than the complete personality mechanism.

A comparable coding architecture is possible:

```text
structured development state
→ local neural control policy
→ frontier LLM code generation
```

The correspondence is:

| Personality architecture       | Coding architecture                                |
| ------------------------------ | -------------------------------------------------- |
| Neural personality state       | Repository and workflow-state encoder              |
| Emotion or motivation dynamics | Risk, uncertainty, progress, and urgency estimates |
| Behavioral policy              | Next-action and model-allocation policy            |
| LLM speaker                    | Code generator, researcher, critic, or explainer   |
| Behavioral reward              | Verified task, process, and efficiency rewards     |
| Safety boundaries              | Deterministic permissions and workflow gates       |

The analogy is useful, but coding has an important advantage: many coding outcomes can be checked mechanically through compilation, tests, static analysis, artifact hashes, policy checks, or formal verification.

The local controller should therefore not be understood as a human-like “brain.” It is better described as a learned policy and state-estimation component that answers bounded questions such as:

* Which worker is most likely to succeed?
* Is another revision worth its cost?
* Should the next step be testing or implementation?
* Is the trajectory stuck?
* Is the current evidence sufficient to request review?
* How likely is the candidate to pass external verification?

# 3. System Architecture

The proposed system contains five independent components.

```text
┌──────────────────────────────────────────────────────────┐
│ 1. Deterministic control kernel                          │
│ State machine, authorization, budgets, immutable gates   │
└──────────────────────────┬───────────────────────────────┘
                           │ legal actions
                           ▼
┌──────────────────────────────────────────────────────────┐
│ 2. Local neural controller                              │
│ Routing, next action, uncertainty, progress, escalation │
└──────────────────────────┬───────────────────────────────┘
                           │ bounded proposal
                           ▼
┌──────────────────────────────────────────────────────────┐
│ 3. Frontier LLM workers                                 │
│ Research, planning, coding, critique, explanation       │
└──────────────────────────┬───────────────────────────────┘
                           │ candidate artifacts
                           ▼
┌──────────────────────────────────────────────────────────┐
│ 4. Independent verification layer                       │
│ Tests, static analysis, formal checks, reviewers        │
└──────────────────────────┬───────────────────────────────┘
                           │ signed evidence
                           ▼
┌──────────────────────────────────────────────────────────┐
│ 5. Deterministic reward machine                         │
│ Updates scores, routing history and bounded privileges  │
└──────────────────────────────────────────────────────────┘
```

## 3.1 Deterministic control kernel

The deterministic kernel owns:

* authoritative workflow state;
* permitted transitions;
* worker identities;
* capability issuance;
* filesystem and network scope;
* repository base and candidate hashes;
* retry and token budgets;
* hidden-evaluation access;
* commit eligibility;
* human-review requirements;
* final effect authorization.

It must not depend on an LLM deciding whether a rule applies.

## 3.2 Local neural controller

The neural controller owns only bounded recommendations:

* choose the next structural action;
* select a model or worker class;
* estimate probability of success;
* estimate uncertainty;
* predict whether verification is needed;
* predict whether another iteration is useful;
* recommend escalation;
* rank several legal candidate plans.

The deterministic kernel masks every illegal action before the neural output can be applied.

## 3.3 Frontier LLM workers

Frontier models may:

* inspect approved context;
* propose plans;
* generate patches;
* write tests in candidate space;
* explain failures;
* critique artifacts;
* produce structured remediation suggestions.

They do not own the workflow state or final verdict.

## 3.4 Independent verification layer

This layer produces evidence through:

* compilation;
* type checking;
* unit and integration tests;
* mutation testing;
* static analysis;
* security scanning;
* model-independent state inspection;
* formal verification where practical;
* human review;
* independently trained verifier models.

## 3.5 Deterministic reward machine

Reward machines represent temporally extended objectives as finite-state machines with sequences, conditions, and loops. They were originally developed to expose reward structure in reinforcement learning and improve learning efficiency. [8]

In the proposed system, the reward machine is not the neural controller. It is deterministic software that converts verified events into structured training and routing signals.

# 4. The Local Neural Controller

## 4.1 Recommended model structure

A practical controller can be significantly smaller than the code-generating models.

One candidate architecture is:

```text
Structured state encoder
        ↓
Shared latent representation
        ├── action-policy head
        ├── model-router head
        ├── success-probability head
        ├── verification-need head
        ├── no-progress detector
        ├── cost/latency estimator
        └── risk/anomaly head
```

The state encoder may be:

* a small transformer over structured event sequences;
* a recurrent neural network;
* a temporal convolutional network;
* an MLP over aggregated features;
* a hybrid embedding and tabular model.

A smaller model is preferable initially because it is easier to train, calibrate, inspect, version, and run locally.

## 4.2 Input state

The neural controller should receive structured state rather than an unrestricted conversation transcript.

Suggested inputs include:

```json
{
  "task_class": "bug_fix",
  "language": "python",
  "repository_size": 184220,
  "changed_files": 3,
  "current_stage": "verification_failed",
  "test_summary": {
    "passed": 412,
    "failed": 2,
    "new_failures": 1
  },
  "static_analysis": {
    "errors": 0,
    "warnings": 4
  },
  "iteration": 2,
  "remaining_budget": {
    "tokens": 62000,
    "tool_calls": 37,
    "wall_seconds": 1180
  },
  "previous_worker": "model_slot_3",
  "failure_categories": [
    "regression",
    "incomplete_edge_case"
  ],
  "artifact_changed": true,
  "progress_delta": 0.31
}
```

Raw proprietary source code can remain in the worker context rather than becoming mandatory router input.

## 4.3 Output actions

The controller should choose only from a closed action set:

```text
OBSERVE
RESEARCH
PLAN
IMPLEMENT
GENERATE_TEST
RUN_TEST
STATIC_ANALYZE
REQUEST_REVIEW
REVISE
COMPARE_CANDIDATES
ESCALATE
SUBMIT_FOR_GATE
ABORT
```

The deterministic controller removes actions that are illegal in the current state.

For example:

```text
Current state: IMPLEMENTATION_PENDING

Legal:
- IMPLEMENT
- RESEARCH
- ESCALATE
- ABORT

Illegal:
- COMMIT
- MERGE
- DECLARE_TEST_PASS
- READ_HIDDEN_HOLDOUT
```

The neural controller never sees an executable option for an illegal transition.

# 5. Learned Model Allocation

## 5.1 Model routing is feasible

RouteLLM, FrugalGPT, RouterBench, and LLMRouterBench demonstrate that model routing and cascading can be learned from preference or performance data. RouteLLM reported large cost reductions while preserving most of the stronger model’s benchmark performance in its evaluated settings. FrugalGPT learns cascades of models to balance performance and cost. [2–4, 9]

For coding agents, routing must occur not merely once per user request but at individual trajectory steps. TwinRouterBench was introduced specifically because one-shot routing benchmarks do not measure whether substituting a model at an intermediate agent step preserves downstream task success. Its dynamic track evaluates routing on live SWE-bench trajectories using official task resolution and realized cost. [10]

## 5.2 Router outputs

The allocator may estimate:

[
P(\text{success} \mid s, m)
]

where:

* (s) is the current task and trajectory state;
* (m) is a candidate model.

The routing objective may be:

[
m^*
===

\arg\max_m
\left[
P(\text{success}\mid s,m)
-------------------------

## \lambda_c C(m)

## \lambda_l L(m)

\lambda_r R(s,m)
\right]
]

where:

* (C(m)) is expected cost;
* (L(m)) is expected latency;
* (R(s,m)) is estimated operational risk.

This score chooses among already permitted models. It does not authorize risky actions.

## 5.3 Avoiding vendor bias

A learned router can reduce model-family favoritism only when its labels are based on external outcomes.

The training target should not be:

```text
The Claude orchestrator preferred Claude.
```

It should be:

```text
Claude candidate:
tests passed = true
regressions = 0
human accepted = true
cost = X

GPT candidate:
tests passed = false
regressions = 2
human accepted = false
cost = Y
```

The router should learn which model performs well for a task class, not which model another LLM likes.

## 5.4 Counterfactual routing data

Strong routing data requires running the same task or trajectory state through several model choices.

For every state (s_i):

```text
run model A → outcome A
run model B → outcome B
run model C → outcome C
```

This produces counterfactual supervision:

```json
{
  "state_id": "swe-task-184-step-7",
  "candidates": [
    {
      "model_slot": "A",
      "verified_success": true,
      "cost": 1.42,
      "latency_ms": 24100
    },
    {
      "model_slot": "B",
      "verified_success": false,
      "cost": 0.38,
      "latency_ms": 9200
    },
    {
      "model_slot": "C",
      "verified_success": true,
      "cost": 0.91,
      "latency_ms": 16800
    }
  ]
}
```

This is expensive to collect but much more reliable than preference labels generated by the orchestrator.

## 5.5 Bias audits

Measure allocation by vendor only after conditioning on objective performance.

Relevant metrics include:

[
\text{SelectionGap}_{A,B}
=========================

## P(\text{select }A \mid A,B\text{ equally correct})

P(\text{select }B \mid A,B\text{ equally correct})
]

Also measure:

* false routing rate;
* regret relative to the best available model;
* cost-adjusted success;
* calibration;
* task-class performance;
* same-family allocation skew;
* allocation under anonymized model slots.

Do not force equal vendor usage when one model is objectively better for a specific task class. The objective is evidence-based allocation, not artificial numerical equality.

# 6. Deterministic Reward Engine

## 6.1 Reward vector

The system should not reduce all performance to one scalar.

Use a lexicographic vector:

[
R =
(
R_{\text{safety}},
R_{\text{correctness}},
R_{\text{reliability}},
R_{\text{progress}},
R_{\text{efficiency}}
)
]

The ordering is non-compensatory.

```text
Safety failure:
cannot be offset by fast completion.

Correctness failure:
cannot be offset by low cost.

Vendor independence failure:
cannot be offset by model confidence.
```

## 6.2 Reward sources

Reward only independently observed events.

### Safety

* no prohibited resource accessed;
* no gate bypass attempted;
* no unauthorized write;
* no evaluator-owned file modified;
* no hidden evaluation leaked.

### Correctness

* compilation succeeds;
* required tests pass;
* regressions remain absent;
* external state matches requirements;
* formal proof obligations pass where available.

### Reliability

* repeated runs remain consistent;
* failure recovery succeeds;
* actions are idempotent where required;
* no-progress loops are avoided.

### Progress

* failing-test count decreases;
* verified requirement coverage increases;
* reviewer findings close;
* candidate quality improves according to protected evaluation.

### Efficiency

* token use;
* wall-clock time;
* tool-call count;
* model cost;
* unnecessary retries;
* redundant model invocations.

## 6.3 Reward record

```json
{
  "event_id": "evt-91029",
  "task_id": "task-184",
  "state_before": "VERIFYING",
  "action": "RUN_TEST",
  "actor": "test_executor",
  "artifact_digest": "sha256:...",
  "observations": {
    "passed": 414,
    "failed": 0,
    "regressions": 0
  },
  "reward": {
    "safety": "PASS",
    "correctness": 1.0,
    "reliability": 0.96,
    "progress": 0.42,
    "efficiency": 0.71
  },
  "evidence_digest": "sha256:..."
}
```

The LLM does not create this record.

## 6.4 Reward-to-authority mapping

Reward may affect:

* future model routing;
* whether another bounded repair iteration is granted;
* expected token allocation;
* whether a low-risk task requires redundant review;
* whether a model remains eligible for a task category.

Reward must never affect:

* access to policy files;
* hidden-test access;
* high-impact commit authorization;
* permission to change the reward function;
* permission to override failed tests;
* permission to judge same-family work authoritatively.

# 7. Learned Reward and Verifier Models

## 7.1 Potential value

Learned verifier models can provide dense feedback where execution results are sparse.

SWE-RM reports that its learned reward model improved open software-engineering agents under both test-time selection and reinforcement learning on SWE-bench Verified. Agentic Verifier actively generates discriminative test inputs and reports gains over simpler execution-based verification approaches on competitive-programming benchmarks. [5, 7]

A local verifier may predict:

* patch success probability;
* likely regression risk;
* missing edge cases;
* whether a trajectory is making progress;
* whether another test is needed;
* whether the agent is attempting to satisfy the test superficially.

## 7.2 Proper role

The learned verifier should be used for:

* candidate prioritization;
* early pruning;
* additional-test targeting;
* review routing;
* uncertainty estimation;
* selecting which expensive verification to run.

It should not serve as the final correctness oracle when execution or formal verification is available.

## 7.3 Verification horizon

Recent work characterizes coding-agent verification as a trade-off among scalability, faithfulness, and robustness. It argues that no fixed reward remains sufficient as coding policies become more capable and that verification must co-evolve with the generator. This is new preprint evidence, but it captures the central limitation of any learned reward engine: the verifier is itself a proxy for user intent. [11]

## 8.2 Auxiliary metacognition labels

“Metacognition” can be operationalized as prediction tasks rather than introspective prose.

Train the controller to predict:

* probability the current plan is wrong;
* probability another iteration improves the result;
* probability tests are insufficient;
* probability of no-progress looping;
* probability of model refusal;
* expected remaining cost;
* probability human escalation is needed;
* calibration of its own success prediction.

These predictions create useful internal state without assuming that the model possesses human-like self-awareness.

## 8.3 Training splits

Split data by:

* repository;
* organization;
* time period;
* issue family;
* programming language;
* model version.

A random trajectory-level split may leak nearly identical tasks or repository structures into training and evaluation.

Use a final temporally held-out evaluation set to measure adaptation to new repositories and model versions.

# 9. Training Procedure

## Phase 1: Deterministic logging

Deploy no learned control.

Use the current deterministic workflow to collect:

* task states;
* actions;
* model choices;
* outcomes;
* costs;
* test results;
* reviewer findings;
* human decisions.

## Phase 2: Supervised router

Train the neural model to predict:

* successful next actions;
* best model choice;
* need for verification;
* expected task success.

Run it in shadow mode.

It observes production states and makes predictions but cannot affect execution.

## Phase 3: Offline policy learning

Train the controller from completed trajectories.

Advantage-weighted regression is one candidate because it can learn from higher-return offline trajectories without allowing unsafe online exploration. The learned-harness study used this approach with terminal task rewards while keeping the LLM executor frozen. [1]

## Phase 4: Gated canary deployment

Permit the controller to choose among low-risk legal actions.

The deterministic state machine still:

* masks illegal actions;
* limits budgets;
* requires verification;
* controls termination;
* owns commits.

## Phase 5: Periodic offline retraining

Do not initially allow continuous live weight updates.

Instead:

```text
collect signed trajectories
→ audit and clean data
→ train candidate controller
→ evaluate on protected benchmarks
→ compare to current controller
→ human approve
→ sign model artifact
→ deploy canary
```

This limits reward-feedback instability and simplifies rollback.

## Phase 6: Conservative online adaptation

Only after strong evidence should online adaptation be considered.

Possible methods include:

* contextual bandits;
* conservative offline-to-online RL;
* bounded parameter adapters;
* per-task routing thresholds.

The production controller should never rewrite its own hard constraints.

# 10. Runtime Algorithm

```text
Input:
task T
workflow state S
legal-action set A
available model set M

1. Deterministic kernel computes legal actions A_legal.
2. Neural controller estimates:
      policy over A_legal
      success probability
      risk
      need for verification
      expected cost
3. Neural router ranks permitted models M_legal.
4. Kernel selects or approves bounded proposal.
5. Worker executes inside isolated environment.
6. Independent systems observe artifacts and effects.
7. Deterministic verifiers run.
8. Reward machine creates signed reward event.
9. Workflow state advances only if deterministic predicates pass.
10. Neural controller receives updated state.
11. On refusal, uncertainty, or no progress:
      replace worker, replan, escalate, or terminate.
12. High-impact effects require fresh deterministic authorization.
```

# 11. Vendor-Bias Control

The model allocator may know model identity because it must choose a model. Semantic evaluators do not always need that information.

Use separate views:

```text
Allocator view:
- model identity
- historical verified performance
- cost
- latency
- capabilities

Judge view:
- opaque candidate identifiers
- artifacts
- rubric
- deterministic evidence
```

The allocator should be trained on verified outcomes, while semantic judges should use decision-local blinding.

## 11.1 Conflict rule

A same-family evaluator may provide criticism but cannot be the final authority over a consequential decision concerning that family.

## 11.2 Reward rule

Do not reward “choosing another vendor.”

Reward:

* choosing the objectively correct candidate;
* selecting the lowest-cost model meeting the verified requirement;
* escalating when uncertainty is calibrated;
* avoiding systematic errors.

## 11.3 Counterfactual bias testing

For matched candidate pairs, test:

1. hidden identities;
2. truthful labels;
3. swapped labels;
4. reversed order;
5. normalized formatting;
6. repeated sampling.

Measure whether decisions follow correctness or provenance labels.

# 12. Experimental Evaluation

## 12.1 Research questions

**RQ1.** Does the local neural controller improve task success compared with a hand-written deterministic workflow?

**RQ2.** Does it reduce unnecessary model calls, retries, and tool usage?

**RQ3.** Does learned model allocation outperform a fixed primary-model policy?

**RQ4.** Does the hybrid system reduce harmful same-family preference?

**RQ5.** Does learned verification improve candidate selection without increasing false acceptance?

**RQ6.** Can the system recover when an LLM orchestrator refuses, loops, or selects an illegal transition?

## 12.2 Experimental conditions

### A. Frontier LLM orchestrator

One LLM controls planning, routing, testing, review, and termination.

### B. Deterministic workflow

Fixed state machine with fixed model assignments.

### C. Deterministic workflow plus learned router

The router chooses models; workflow remains fixed.

### D. Learned harness controller

The local controller chooses structural actions and models.

### E. Learned controller plus learned verifier

Adds a local code-quality and progress model.

### F. Full NSCCP

Adds vendor-bias controls, deterministic reward machine, refusal recovery, protected evaluations, and human escalation.

## 12.3 Public benchmarks

### SWE-bench Verified

Measures end-to-end issue resolution through executable repository tests.

### RouterBench

Provides multi-model response and quality data for evaluating learned routers. [3]

### LLMRouterBench

Contains more than 400,000 instances covering 21 datasets and 33 models, with performance and cost-routing metrics. Its authors report that several sophisticated routers fail to reliably outperform simple baselines under unified evaluation, making it useful for avoiding overstated routing claims. [4]

### TwinRouterBench

Supports step-level and live routing evaluation for agentic workloads, including SWE-bench trajectories. [10]

### Control-oriented coding tasks

AI Control provides an established experimental framing in which a powerful model is treated as untrusted and protocols are evaluated for their ability to prevent subtle incorrect code from being accepted. [12]

## 12.4 Metrics

### Correctness

* resolved tasks;
* false acceptances;
* false rejections;
* regressions;
* hidden-test reliability;
* mutation score.

### Control quality

* illegal transition attempts;
* gate violations;
* refusal recovery;
* loop frequency;
* premature submission;
* skipped verification.

### Router quality

* success regret relative to the best available model;
* cost-adjusted success;
* latency;
* calibration;
* model-selection entropy;
* vendor-conditioned selection error.

### Reward integrity

* reward/outcome correlation;
* evidence tampering attempts;
* proxy score improvement without task improvement;
* test modification or evaluator manipulation;
* protected-set overfitting.

### Efficiency

* total model calls;
* tokens;
* wall time;
* tool calls;
* verifier cost;
* human escalations.

# 13. Reward-Hacking Tests

Reward-model overoptimization research demonstrates that optimizing an imperfect reward model too aggressively can cause true performance to deteriorate even while proxy reward continues increasing. [13]

Language-model feedback loops can also produce in-context reward hacking during deployment without changing model weights. [14]

The evaluation must therefore include deliberate reward attacks:

* modify tests rather than fix code;
* remove difficult tests;
* generate trivial patches;
* hide failures from logs;
* repeatedly ask for clarification to avoid penalties;
* submit early to reduce cost;
* create artificial work and then claim progress;
* produce many low-value findings;
* manipulate verifier inputs;
* choose a favored vendor despite contrary evidence;
* exploit uncertainty thresholds;
* imitate successful trace patterns without performing the work.

The system should detect:

```text
proxy score rises
AND
external task quality does not rise
→ suspected reward hacking
```

# 14. Strict Critique

## 14.1 The neural controller can become a new orchestrator failure

Replacing an LLM orchestrator with a neural controller does not eliminate control risk. It changes the form of the risk.

A learned controller may:

* route systematically to familiar models;
* overfit to historical repositories;
* under-escalate unusual tasks;
* exploit reward proxies;
* become poorly calibrated after model upgrades;
* produce brittle behavior under distribution shift.

It must remain constrained by deterministic masks.

## 14.2 Historical data can encode vendor bias

If earlier Opus orchestration rejected non-Anthropic work unfairly, training directly on historical acceptance decisions may teach the local controller the same bias.

Training labels must prioritize:

* executable outcomes;
* independent human review;
* externally confirmed correctness;
* balanced counterfactual comparisons.

Do not treat the prior orchestrator’s verdict as ground truth.

## 14.3 Learned verifiers can be confidently wrong

A verifier may learn superficial code patterns, framework conventions, patch size, or style instead of correctness.

Execution-free reward models are useful for ranking and triage but should not override tests.

## 14.4 Tests are incomplete

Even deterministic tests are proxies for intended behavior.

Passing tests should mean:

> The candidate passed the available verification suite.

It should not mean:

> The candidate is universally correct.

## 14.5 Training may reward test gaming

The more tightly a coding model is optimized against a fixed verifier, the more likely it becomes to exploit its weaknesses. Reward suites and verifier models must evolve.

## 14.6 Online learning increases operational risk

A continuously adapting controller is harder to reproduce, audit, and roll back.

Offline, versioned retraining is the safer initial design.

## 14.7 Complexity may exceed benefit

The architecture introduces:

* controller training;
* model routing;
* reward processing;
* feature engineering;
* counterfactual data generation;
* verifier calibration;
* protected evaluations;
* model lifecycle management.

For simple tasks, a fixed deterministic workflow may be better.

## 14.8 Human oversight remains necessary

Novel product decisions, ambiguous specifications, security-sensitive changes, and unresolved evaluator disagreements require human judgment.

---

# 15. Is This a Good or Bad Idea?

## Good idea when

* substantial coding volume justifies training infrastructure;
* multiple models exhibit complementary strengths;
* verified trajectory data is available;
* deterministic tests and gates already exist;
* cost and reliability matter enough to optimize;
* the learned controller can be deployed in shadow mode;
* rollback and model versioning are mature.

## Bad idea when

* the neural controller becomes the permission authority;
* reward is based mainly on LLM opinions;
* training labels inherit the current orchestrator’s bias;
* online self-modification begins before calibration;
* the reward model can change its own evidence;
* executable tests are replaced by learned confidence;
* the architecture is introduced before reliable logging exists.

The strongest formulation is:

> Use the neural network to learn judgment under uncertainty. Use deterministic software to define authority.

# 17. Conclusion

A coding system resembling your earlier personality architecture is technically possible.

Its strongest form is not:

```text
Neural brain
→ unrestricted LLM body
```

It is:

```text
Deterministic skeleton
→ learned neural coordination system
→ frontier LLM language and code engine
→ independent verification
```

The deterministic layer establishes what may happen.

The neural controller learns what is likely to work efficiently.

The frontier LLM performs expressive and generative work.

The verification layer determines what actually happened.

The reward machine converts verified outcomes into controlled future learning and routing signals.

This division allows the system to benefit from learned behavior and metacognitive prediction without making the learned model the final authority.

The central claim is:

> A locally trained neural controller can improve coding-agent routing, verification, retry, and stopping behavior, but reliability depends on keeping authorization, evidence, and irreversible effects outside the learned policy.
