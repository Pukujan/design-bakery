Black-box and grey-box validation of autonomous agent work

Pujan · Design Bakery

db-r-2026-004 · submitted 2026-07-22 · status pending

Owner gate. Design-descriptive working paper. It states a validation method and its test plan; it makes no benchmark claim. Cited concepts are established software-testing ideas; empirical cells stay empty until the owner marks the paper approved.

Abstract

If an autonomous agent produces work, who checks it? Not the agent, and not — when the checker shares the agent's model family — an unconstrained model judge. This paper separates two validation modes for agent output. Black-box validation asks only whether the observable outcome is correct: an outcome oracle over external state. Grey-box validation additionally checks how the work was done against invariants it should never violate: a process oracle. The organising rule is that a deterministic checker, never a model vote, decides pass or fail; models only advise. We also describe why a fully blind holdout is the wrong tool for validating existing code, and how a grey-box holdout — given real signatures but not implementations — fixes it.

1. The oracle problem, for agents

Software testing calls the mechanism that decides whether an output is correct the test oracle, and notes that a good oracle is often the hard part [1]. For autonomous agents the oracle problem is sharper: the thing being checked can also argue about its own correctness. So the oracle must be external to the agent and, ideally, deterministic.

2. Black-box: the outcome oracle

Treat the agent as opaque; judge only the externally observable result — tests pass or fail, a type check succeeds, a schema validates, produced state matches expected state. Where a single reference output is unavailable, established black-box techniques still apply: metamorphic relations (known relationships between inputs and outputs that must hold) [2] and differential testing (compare against an independent implementation) [3]. None of these consult the agent's reasoning.

3. Grey-box: the process oracle

Outcome-correct is not always process-correct: a result can pass its visible tests while violating an invariant (an unlogged side effect, a bypassed boundary, a hidden write). Grey-box validation adds checks on the trajectory — invariants that must hold regardless of the result — without trusting the agent's narration. In the Cortex setting these invariants are concrete: authorization precedes effect, the broker is the sole writer, every request yields a receipt.

4. Blind vs. grey-box holdouts

A common anti-gaming device is a holdout: an independent party writes hidden tests. For validating a new build against a spec, a blind holdout is right. But for validating existing code, a blind holdout that must guess the real interface tends to test its own guesses and produce false failures. The fix is a grey-box holdout: give the holdout author the real signatures (extracted structurally — types and shapes, not bodies) so tests target the actual contract, while the implementation stays hidden.

5. Deterministic evidence dominates

Across both modes the same rule holds: a deterministic checker decides pass/fail and a model vote never overrides executable evidence. "Tests fail and the model says it is correct" is a failure. Models are useful as advisors — proposing cases, explaining a diff, flagging a smell — but not as the authority in the verdict path. An evaluator that is never itself attacked with defective and alternate-valid cases is not authoritative.
