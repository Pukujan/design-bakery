Deny-by-default authorization for tool-using agents: the Cortex kernel model

Pujan · Design Bakery

db-r-2026-002 · submitted 2026-07-22 · status pending

Owner gate. This is a design-descriptive working paper. It states an authorization model and its invariants; it makes no benchmark, latency, or production-governance claim. Numeric results remain empty until the owner marks the paper approved in catalog.js.

Abstract

A capable agent decides what to attempt; it does not, by itself, decide what may become a committed effect. Cortex is an execution kernel that sits beneath agent reasoning and owns that second decision. This paper describes the kernel model — a structured request, a deny-by-default check, explicit and scoped authority, a policy gate evaluated at the point where the concrete effect is known, tool execution routed through a single broker, a sole-writer commit path, and a content-bound receipt for every outcome. The model is a restatement of two classical security principles — the reference monitor and least privilege — specialised for tool-using agents. We separate component-tested mechanisms from composition status and make no production claim.

1. Problem

An agent with tools can cause external effects: writes, calls, transactions. If authority is implicit in tool access — "the agent could call it, so it may" — then reasoning quality, conversational context, or possession of a tool name become de-facto authorization. That is the failure this kernel exists to prevent. The requirement is a boundary that is separate from the agent, evaluates every proposed effect, and is deny-by-default.

2. The model

Seven mechanisms compose one controlled path from a proposal to a committed state change:

  1. Request envelope. Actor, intent, target, context, and presented authority are structured before execution — a free-form model message is not itself an execution contract.
  2. Deny by default. Missing, unknown, invalid, or insufficient authority resolves to a refusal.
  3. Explicit authority. A declared grant whose operation and target scope cover the request.
  4. Policy gate. Current constraints are evaluated at the boundary where the concrete effect is known, not earlier when only intent is visible.
  5. Brokered tools. Allowed tool execution crosses the effect boundary through a single broker, not by direct agent access.
  6. Sole-writer commit. Controlled writes are concentrated in the broker so authorization cannot be bypassed by a parallel path.
  7. Execution receipts. Every completed or denied request returns evidence binding the proposal, the decision, the broker outcome, and the resulting state.

3. Invariants

An implementation preserves these regardless of the agent, model, tool, or application attached to it:

  • A request is denied unless sufficient authority is established (default deny).
  • Authority applies to declared operations and targets, not general intent (explicit scope).
  • The broker is the only component permitted to commit controlled state (sole writer).
  • Authorization completes before a requested write is committed (decision before effect).
  • Allowed, denied, and failed requests all return evidence of their path (receipt after decision).

These restate the reference-monitor idea — a mediation point that is always invoked, tamper-resistant, and small enough to verify [1] — and least privilege / least authority [2], applied to agent effects.
