Deny-by-default authorization for tool-using agents: the Cortex kernel model

Pujan · Design Bakery

db-r-2026-002 · submitted 2026-07-22 · status pending

Owner gate. This is a design-descriptive working paper. It states an authorization model, its invariants, a decision procedure, and an evaluation protocol; it makes no benchmark, latency, or production-governance claim about a running Cortex deployment. Numeric results remain empty until the owner marks the paper approved in catalog.js. Where the paper cites results, those are other authors' published figures, attributed by reference.

Abstract

A capable agent decides what to attempt; it does not, by itself, decide what may become a committed effect. We describe Cortex, an execution kernel that sits beneath agent reasoning and owns that second decision. The kernel accepts a structured request describing an actor, an intent, a target, a context, and presented authority; refuses by default; requires an explicit, scoped grant; evaluates policy at the point where the concrete effect is known; routes any allowed effect through a single broker that is the sole writer of controlled state; and returns a content-bound receipt for every outcome, allowed or denied. We argue that this is not a new security idea but a specialisation of two classical ones, the reference monitor (a mediation point that is always invoked, tamper-resistant, and small enough to verify) and least privilege, to the setting where the principal proposing effects is a probabilistic model. We give the request contract, the authorization decision procedure, the kernel invariants, and the receipt structure; relate the model to recent work on programmable privilege and control/data-flow separation for LLM agents; and specify an evaluation protocol that a deterministic checker, not a model judge, would run. We separate component-tested mechanisms from composition status and make no claim of a governed production deployment.

1. Introduction

An agent equipped with tools can cause external effects, it can write records, call services, move money, change files. The question this paper is about is not whether the agent is smart enough to choose a good action, but whether the system can guarantee that a proposed action becomes a committed effect only when it is explicitly authorized under current policy. When authority is implicit in tool access, "the model was able to call the tool, therefore it may", then reasoning quality, conversational context, or mere possession of a tool name silently become authorization. That substitution is the failure this kernel exists to prevent.

Cortex is a kernel, not a smarter agent. Its responsibility begins at the moment an actor proposes an operation that could produce an external effect or a committed state change, and ends when that proposal has been either refused or turned into an authorized, brokered, receipted effect. Planning, model selection, prompt construction, and general task reasoning remain deliberately outside the kernel. This paper contributes:

  • a request contract that makes a proposed effect concrete enough to authorize (§4);
  • a deny-by-default authorization decision procedure, evaluated at the effect boundary, with an explicit sole-writer commit path (§5);
  • a set of kernel invariants that hold regardless of the agent, model, tool, or application attached to the kernel (§6);
  • a content-bound receipt structure that records the proposal, the decision, the broker outcome, and the resulting state for every request, allowed or denied (§7);
  • a mapping to classical and contemporary access-control work, and an evaluation protocol that relies on deterministic checks rather than model judgement (§8–§9).

2. Threat model and assumptions

We assume the agent is capable but not trusted with authority: it may propose any operation, including operations it should not be allowed to perform, and it may produce fluent justifications for them. We do not assume the agent is adversarial in the cryptographic sense, but the kernel must be correct even if the agent is wrong, confused, prompt-injected, or optimising for task completion at the expense of a constraint. Concretely, the kernel must resist: authority implied by tool availability; a persuasive natural-language argument standing in for a grant; an effect authorized against stale context and then committed after the authorizing evidence is no longer valid; and a second, parallel write path that bypasses the authorization boundary.

We assume a trusted computing base consisting of the kernel's decision procedure, the broker, and the receipt store; these must be small, testable, and auditable. We do not assume the policy itself is correct, an incorrect policy will authorize the wrong things, only that the kernel faithfully enforces whatever policy it is given, deny-by-default, at the effect boundary. Out of scope: sandbox escape at the operating-system level, compromise of the broker's own credentials, and supply-chain compromise of the kernel binary; these are the concern of the surrounding platform.

3. System model and notation

A request r is proposed by an actor and carries an intent (the operation class), a target (the concrete object of the operation), a context (the state the proposal was formed against), and presented authority (the grant the actor claims covers the request). A grant g declares an operation set and a target scope. A policy P is a predicate evaluated at the effect boundary, the point at which the concrete effect is known, not the earlier point at which only intent is visible. The broker B is the single component permitted to perform controlled effects and commit controlled state. A receipt binds a request to its decision and observed outcome.

The kernel decides a function authorize(r, g, P) → {ALLOW, DENY}. An ALLOW proceeds through B; a DENY, including the absence of a decision, proceeds to a refusal. Both paths produce a receipt. The kernel does not itself plan, choose models, or interpret free-form text; it evaluates the contract it is handed.

4. The request contract

The authorization boundary needs a structured description of what is being requested; a free-form model message is not itself an execution contract. The request envelope therefore structures, before execution, the fields the decision procedure consumes: 

request := {
 actor: principal proposing the operation
 intent: operation class (e.g. write.customer_note)
 target: concrete object + scope of the effect
 context: state / evidence the proposal was formed against
 authority: the grant presented as covering this request
}

Structuring the request is what makes deny-by-default meaningful: a decision procedure can only refuse "unless sufficient authority is established" if there is a declared thing to check the authority against. The envelope also carries the material later bound into the receipt, so that the record of a decision references exactly the request that was decided.

5. The authorization decision procedure

Seven mechanisms compose one controlled path from a proposal to a committed state change. They are, in order: (1) the request envelope above; (2) deny by default, missing, unknown, invalid, or insufficient authority resolves to a refusal; (3) explicit authority, a declared grant whose operation and target scope cover the request; (4) the policy gate, current constraints evaluated where the concrete effect is known; (5) brokered tools, allowed execution crosses the effect boundary through B, not by direct agent access; (6) sole-writer commit , controlled writes are concentrated in B so authorization cannot be bypassed by a parallel path; and (7) execution receipts, evidence returned for every outcome. The conceptual kernel path is small: 

decision = authorize(request, authority, policy)

if decision != ALLOW:
 return receipt(request, decision, no_effect) # refusal is still receipted

result = tool_broker.execute(request.operation) # sole writer performs the effect
return receipt(request, decision, result) # bind proposal, decision, outcome

Two properties of this procedure are load-bearing. First, the policy gate is evaluated at the effect boundary: authorizing against intent alone permits a class of failures in which an operation is approved and then committed after the authorizing evidence has gone stale. Re-checking authorization immediately before a durable effect is the mitigation. Second, the commit path is a sole writer: if any other path could write controlled state, the authorization decision would be advisory. Concentrating writes in B makes the decision binding.

6. Kernel invariants

An implementation preserves these regardless of the agent, model, tool, or application attached:

  • INV-1 Default deny. A request is denied unless sufficient authority is established.
  • INV-2 Explicit scope. Authority applies to declared operations and targets, not general intent.
  • INV-3 Brokered effects. Authorized tool execution crosses the effect boundary through the broker.
  • INV-4 Sole writer. The broker is the only component permitted to commit controlled state.
  • INV-5 Decision before effect. Authorization completes before a requested write is committed.
  • INV-6 Receipt after decision. Allowed, denied, and failed requests all return evidence of their path.

INV-1 and INV-2 are the deny-by-default core; INV-3 and INV-4 make the decision non-bypassable; INV-5 orders the decision before the effect; INV-6 makes the whole path accountable. A failure of any one degrades the others: without a sole writer, "decision before effect" can be routed around; without receipts, a denial cannot be distinguished from a silent success.

7. Execution receipts

A receipt is the kernel's evidence object. It binds, for a single request, the proposal that was made, the authorization decision and the policy it was evaluated under, the identity of the writer, and the observed outcome and resulting state reference: 

receipt := {
 request_ref: the exact proposal (actor, intent, target, context)
 decision: ALLOW | DENY, with the policy reference evaluated
 writer: that the controlled commit path stayed with the broker
 outcome: whether an effect occurred, and the resulting state ref
}

Because a receipt is produced for a denial as well as a success, the receipt log distinguishes "the request was refused" from "the request silently did nothing", a distinction that black-box outcome checking alone cannot always make (an unauthorized transfer that does not happen because the payment service crashed looks, externally, like a correctly refused transfer). Receipts are the process evidence a grey-box validator consumes; see the companion validation paper [3] and the discussion of trace trustworthiness there.

8. Relationship to classical and contemporary work

The invariants are a restatement of the reference-monitor concept, a mediation point that is always invoked, tamper-resistant, and small enough to be verified [1], and of least privilege [2], applied to agent effects rather than to processes or users. The request contract plays the role of the mediated operation; deny-by-default and explicit scope are least privilege; the sole writer is the always-invoked property; receipts are the auditability property.

Recent work brings these principles to LLM agents specifically. Programmable privilege control such as Progent expresses fine-grained, deterministic policies over tool names, arguments, and context, with fallback behaviour [4], the policy-gate analogue at the tool layer. Control/data-flow separation such as CaMeL keeps a trusted control plane distinct from untrusted data and mediates effects through a capability-checking interpreter [5], the same instinct as brokered effects and a sole writer. General policy engines and analyzable authorization languages, OPA's decision/enforcement separation [6] and Cedar's analyzable policies [7], are candidate implementations of the policy gate. Per-worker cryptographic identity [8] and signed step metadata [9] are candidate implementations of "who was the writer" and of receipt integrity. Cortex's contribution is not a new primitive but the specific composition, envelope, deny-by-default, explicit scope, effect-boundary policy, sole writer, receipts, presented as a kernel with stated invariants.

9. Evaluation methodology (no results claimed)

The kernel is designed to be evaluated by deterministic checks, not by a model's opinion. We specify the protocol; we report no numbers. A conforming test suite would establish, per mechanism:

  • Default deny. For a corpus of requests with missing / unknown / invalid / insufficient authority, the decision is DENY and no controlled write occurs (checked against the system of record, not the agent's self-report).
  • Explicit scope. A grant covering operation x on target t does not authorize x on t′ outside scope, nor a different operation on t.
  • Decision before effect / effect-boundary freshness. An authorization formed against context that becomes invalid before commit does not commit; a metamorphic check (revoke the grant between decision and commit → the effect must flip allow→deny).
  • Sole writer. An attempt to commit controlled state through any path other than the broker fails closed.
  • Receipt completeness. Every request, allowed, denied, failed, yields a receipt whose request_ref matches the exact proposal and whose outcome matches the independently observed state.

This is a black-box outcome oracle over external state plus a grey-box process oracle over the invariants, in the sense of [3]; deterministic evidence decides pass or fail, and no model vote overrides an executable contradiction. The evaluator itself should be challenged with deliberately defective cases (a superficially successful but unauthorized write; an unlogged side effect) before it is trusted, an evaluator never attacked is not authoritative [3].

10. Limitations and non-claims

  • The kernel enforces whatever policy it is given; an incorrect policy authorizes the wrong effects. Policy correctness is out of scope here.
  • Per-request authorization is necessary but not sufficient: individually valid operations can compose into an invalid sequence, which needs sequence- and commit-level policy in addition to the per-effect gate.
  • Moving authority out of the agent does not delete the root of trust; it relocates it to the policy, the broker, and the receipt store, which must be smaller and more auditable than the agent.
  • This paper claims no live production-governed runs and treats builder self-report as not independent evaluation; composition status is tracked separately [10].
  • No pass rates, latencies, or coverage figures are asserted; benchmark cells are empty pending owner approval.
