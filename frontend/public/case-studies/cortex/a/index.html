Don't trust the agent.

Cortex is not a smarter agent. It is the machinery around the agent: a memory that keeps a months-long project coherent, retrieval that finds the right context instead of guessing, an evaluation harness where checkers rather than opinions decide pass or fail, and a kernel that decides which effects are allowed to happen at all. The kernel is the part that can say no. The rest is what makes saying yes worth anything.

The problem

Capable is not the same as trustworthy.

AI coding agents are good and getting better. But you still can't trust the output without checking it, and checking costs about what the work did. The usual answer is "make the agent smarter." That lowers the error rate. It never gives you a guarantee. For software that ships, "usually correct" isn't trustworthy at all.

Everyone else

A better driver

Stronger models, richer prompts, more tools. The agent is still the thing being trusted, so a wrong decision is a wrong action you find out about later. A probabilistic system gives you a probability. Never a proof.

Cortex

The seatbelt, the crumple zone, the guardrail

Assume the agent is fallible by default. Put the trust in a kernel that sits between the agent and the codebase and mechanically forbids anything the contract didn't allow. Now any driver is safe enough.

The inversion

The move operating systems made fifty years ago, applied to AI agents.

You don't trust every program not to corrupt memory; you put a kernel between programs and the hardware that makes it impossible. Cortex is that kernel for an agent acting on a repository. Three commitments follow.

01 · before

Contract-first

The agent researches, asks the questions that actually matter, and a frozen contract (goal, exact write-set, acceptance test) is agreed before any code gets written. The target stops moving mid-build.

02 · during

Deny-by-default

Every action is checked against the frozen contract by a reference monitor with no model in the verdict. Guessing is not a legal move; unresolved unknowns are a denial, not a coin-flip.

03 · after

Proof, not vibes

Nothing merges without a deterministic verdict from an identity the agent can't impersonate, and a receipt of exactly what was approved. Past failures become permanent gates.

The kernel · Phase 0

Seven mechanisms. Each one a proven idea, none of them a language model.

The trust root every later capability stands on. None of these are new inventions. They're the load-bearing patterns of operating-system security, borrowed for a new domain. The evidence is further down.

built
authorize()

Reference monitor

A pure, deny-by-default gate. Canonicalizes every path against an adversarial corpus and admits only writes inside the frozen contract. No credentials, no model, no I/O in the verdict.

wiring
tool_broker

Sole writer

The only process that can touch the repo. Holds all credentials, runs as its own user, polls rather than listens, opens pull requests. Agents hold nothing and cannot push.

built
receipts

Unforgeable receipts

Every approval mints a single-use receipt bound to the exact content hash. "Approve, then swap the diff" becomes mechanically detectable. Tamper-evident and spent-once, atomically.

next
isolation

Trust-graded sandboxes

Untrusted free-fleet code runs under stronger isolation, the owner's strong-model code under lighter. A workload that can't run at its grade fails loudly. It never gets quietly downgraded to a weaker one.

next
human_control

Approval bound to the diff

You approve on a faithful summary from an independent path, and the server binds it to the exact diff underneath. A bad summary can mislead judgment; it can never change what was approved.

next
oracles

Evidence, not assertion

Deterministic checkers decide pass/fail; a separate identity attests; a verifying action re-checks the evidence hash. No judge where a checker can decide. Every result carries a bundle.

The learning loop closes it. Failures get fingerprinted, and the ones that recur become new gates once a human signs off, so the same class of bug never ships twice. Every cycle leaves the kernel a little harder to fool.

Several projects arrived at the same workflow layer on their own: decompose a goal, run parallel workers, track evidence. But every one of them trusts the agent to do the right thing. None has the reference monitor, the content-bound receipts, or the sole-writer broker. That's the half Cortex adds.
Why this isn't a leap in the dark

Every mechanism is decades-proven. The novelty is the composition.

Each part of the kernel is a battle-tested pattern with production and literature behind it. This stands on named, cited work. It doesn't invent new security primitives.

1972

The reference monitor

Anderson's study, then Saltzer & Schroeder (1975): least privilege, complete mediation, fail-safe defaults. It's how SELinux, seccomp, and every OS kernel work. authorize() is this.

2003

Privilege separation

OpenSSH's tiny privileged monitor with unprivileged workers that hold nothing (Provos, Friedl, Honeyman, USENIX Security). The broker is this pattern.

2009

Capability & content binding

seL4, the formally-verified capability microkernel. Macaroons (Google, 2014). Merkle hashing, which binds a token to an exact hash the way git and Sigstore do. The receipt is this.

2020

Trust-graded isolation

Firecracker microVMs run every AWS Lambda (Agache et al., NSDI); gVisor runs Google Cloud Run. Grading untrusted code into stronger sandboxes is how all serverless works.

Eight in-house prior-art studies and two independent cross-vendor critique rounds went in before the kernel was designed. Off-the-shelf parts were adopted where they fit and rejected, with reasons, where they didn't. What's genuinely new is that composition, applied to AI agents. The verification floors de-risk it, and on this project they've already caught real defects in code that had passed every visible test.

Two results worth reporting because they went against us. The rubric that lifted a capable judge to 0.92 pushed a small local model down from 0.60 to 0.52, so rubric complexity has to match the judge. And on our own gold set, judges from the same model family that wrote the labels agreed at 0.95 while other families managed 0.50. That is a self-preference problem, so nothing was promoted to training gold and the judge-free harness above exists because of it. An evaluation that flatters its author is not an evaluation.
Status · self-hosting

The kernel is being built by its own rules.

Every module ships as a pull request authored by the broker's own identity, reviewed and approved through the same gates it will use in production. The thing that will build trustworthy software is, right now, building itself that way.
