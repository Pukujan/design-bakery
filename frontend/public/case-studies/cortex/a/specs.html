01 / Purpose

Control effects beneath agent reasoning.

Cortex is a kernel, not a smarter agent. Its responsibility begins when an actor proposes an operation that could produce an external effect or committed state change.

The kernel evaluates whether that request carries explicit authority under current policy. An allowed request proceeds through tool_broker. A request without sufficient authority is denied. Both paths produce evidence of the decision.

Core rule

Reasoning quality does not confer authority. Confidence, intent, conversational context, and access to a tool name are not substitutes for an explicit authorization decision.

Boundary

Cortex owns authorization at the effect boundary, the brokered write path, and the receipt that binds a request to its observed outcome. Planning, model selection, prompt construction, and general task reasoning remain outside the kernel.

02 / Invariants

Properties that must remain true.

A Cortex implementation preserves these invariants regardless of the agent, model, tool, or application attached to it.

INV-01 Default deny

A request is denied unless sufficient authority is established.

INV-02 Explicit scope

Authority applies to declared operations and targets, not general intent.

INV-03 Brokered effects

Authorized tool execution crosses the effect boundary through tool_broker.

INV-04 Sole writer

tool_broker is the only component permitted to commit controlled state.

INV-05 Decision before effect

Authorization completes before a requested write is committed.

INV-06 Receipt after decision

Allowed, denied, and failed requests return evidence of their path.

03 / Execution flow

One controlled path from proposal to state.

01 / Input Receive structured request

The actor, intent, target, context, and presented authority enter the kernel together.

02 / Gate Evaluate authority and policy

The kernel resolves an explicit allow or deny decision. Absence of proof resolves to deny.

03 / Dispatch Submit allowed operation to tool_broker

The broker owns the controlled tool invocation and write path.

04 / Commit Observe resulting state

An allowed write is committed through the sole writer, or execution fails without an alternate path.

05 / Evidence Return receipt

The receipt connects request, decision, execution outcome, and resulting state reference.

# conceptual kernel path
decision = authorize(request, authority, policy)

if decision != ALLOW:
    return receipt(request, decision, no_effect)

result = tool_broker.execute(request.operation)
return receipt(request, decision, result)

04 / Request contract

Make the proposed effect concrete.

The authorization boundary needs a structured description of what is being requested. A free-form model message is not itself an execution contract.

Field Purpose Authorization relevance
request_id Identifies one proposed effect. Correlates decision, execution, and receipt.
principal Names the actor making the request. Provides the subject against which authority is evaluated.
intent Names the requested class of operation. Must fall within an allowed operation scope.
target Identifies the object or resource affected. Prevents broad authority from being inferred from a tool name.
context Carries facts needed for policy evaluation. May constrain a decision but does not independently grant authority.
authority Presents the explicit capability or grant. Must be valid and sufficient for the operation and target.

05 / Authorization

Deny unless the request proves it may proceed.

Authorization is an explicit kernel decision over the principal, requested operation, target, presented authority, and applicable policy.

ALLOW

The authority is valid, its scope covers the concrete operation and target, and policy permits execution.

DENY

Authority is missing, invalid, insufficient, out of scope, or rejected by policy. No write is dispatched.

Deny-by-default requirement

An unknown, incomplete, or indeterminate authorization state must resolve to denial. It must not fall through to tool execution.

Decision inputs

Input Question Insufficient result
Principal Who is asking? Deny
Operation What effect is requested? Deny
Target Which concrete resource would change? Deny
Authority What explicit grant covers this request? Deny
Policy Do current constraints permit the effect? Deny

06 / Tool broker

The sole writer owns the commit path.

tool_broker is the only component permitted to turn an authorized request into controlled external effect or committed state.

Agents may discover tools, select tools, prepare arguments, and propose invocations. Those activities do not grant a second write path. Execution is submitted only after authorization and remains attributable to the broker.

Sole-writer requirement

An integration that allows an agent, planner, wrapper, or side channel to perform the same controlled write outside tool_broker violates the Cortex boundary.

Broker responsibilities

Responsibility Required behavior
Accept authorized dispatch Operate on the request approved by the kernel, without silently broadening its target or operation.
Own write access Keep controlled write credentials and commit capability out of the agent's independent reach.
Report outcome Return success, denial, or execution failure with enough identity to construct a receipt.
Preserve correlation Carry the request and decision identifiers across dispatch and result handling.

07 / Receipts

Bind authority to the observed outcome.

A receipt is the evidence returned by the kernel after an authorization decision and, for allowed requests, broker execution.

Receipts distinguish denial from execution failure and distinguish both from a committed effect. They preserve the chain from proposal to resulting state rather than treating a tool response as sufficient proof.

Receipt data What it establishes
Request reference Which proposed effect was evaluated.
Principal and intent Who requested which class of operation.
Decision and policy reference Whether execution was authorized and under which evaluated policy.
Writer identity That the controlled commit path remained with tool_broker.
Outcome and state reference Whether an effect occurred and which resulting state was observed.

08 / Seven mechanisms

The complete control path.

  1. Request envelope

    Structures the actor, intent, target, context, and presented authority before execution.

  2. Deny by default

    Resolves missing, unknown, invalid, or insufficient authority to a refusal.

  3. Explicit authority

    Requires a declared grant whose operation and target scope cover the request.

  4. Policy gate

    Evaluates current constraints at the boundary where the concrete effect is known.

  5. Brokered tools

    Routes allowed tool execution through tool_broker instead of direct agent access.

  6. Sole-writer commit

    Concentrates controlled writes in the broker so authorization cannot be bypassed by a parallel path.

  7. Execution receipts

    Return evidence connecting the proposal, authorization decision, broker outcome, and resulting state.

Cortex / case study

The boundary around useful agency.

Cortex is an execution kernel for tool-using agents. It does not make an agent smarter. It makes every proposed action explicit, authorized, bounded, and accountable.

The proposition

Intelligence proposes. The boundary decides.

Cortex separates a model's reasoning from the effects that reasoning can cause. The kernel receives an intended action, evaluates it against authority and policy, and records what happened.

Authorization is a control point, not a prompt.

In an open-ended agent loop, a useful answer is only part of the job. The system also needs a dependable answer to: what was requested, what was allowed, which tool performed it, and what evidence remains?

Cortex puts those questions in a small, inspectable execution path. By default, a proposed action is denied until it has the authority and context required to proceed.

The kernel is not a smarter agent. It is the part that keeps an agent's reach smaller than its imagination.

The architecture

Seven mechanisms make the boundary real.

Each mechanism answers a different failure mode in the path from intent to side effect. Together they turn a vague tool call into a governed execution.

01 / intent

Explicit action requests

Proposals become structured requests rather than invisible side effects.

02 / authority

Deny by default

An action must be authorized before the system permits it to continue.

03 / policy

Bounded decisions

Policy evaluates the requested operation, its target, and the available context.

04 / mediation

One tool broker

tool_broker is the sole writer. Tools do not bypass the execution boundary.

05 / evidence

Receipts

Each decision and resulting execution has a durable, inspectable record.

06 / continuity

Traceable context

Requests, decisions, and outcomes stay connected through an execution trace.

07 / control

Observable status

The system exposes whether work is proposed, denied, executing, or complete.

Field comparison

Capability without a blank cheque.

The useful distinction is not whether an agent can call a tool. It is whether the surrounding system can constrain and explain that call.

Unbounded agent loop

Reasoning and effects share a path.

Tool access is treated as an extension of the model's loop, making authority and outcome difficult to inspect independently.

  • Permission may be implicit
  • Writes can be scattered across tools
  • Evidence is assembled after the fact
Cortex execution

Reasoning meets a governed boundary.

The model can propose useful work while the kernel remains responsible for authorization, mediation, and the record.

  • Denial is the starting state
  • tool_broker is the sole writer
  • Receipts follow the execution path

The artifact

Every allowed action leaves a receipt.

A receipt makes a decision legible after the model has moved on. It ties the requested action to its authorization, broker, result, and current status.

Cortex / technical specifications

A small execution path with a clear perimeter.

These specifications describe the boundary between an agent's proposed intent and the tools that can produce effects. Cortex is the kernel and control path, not a replacement for the agent.

Execution flow

From proposal to receipt.

The flow is intentionally directional. A request moves through authorization before the broker can perform a write, and the outcome is returned as an inspectable receipt.

01

Agent proposes

The agent emits an explicit action request with the operation and target it wants to use.

intent -> action_request
02

Kernel normalizes

Cortex places the request into the governed execution path and gives it a traceable identity.

action_request -> request_id
03

Policy evaluates

Authorization is deny-by-default. The requested action must be allowed by the applicable authority and policy context.

request + policy -> allow | deny
04

Broker mediates

Only tool_broker may write. A denied request stops here; an allowed request is passed to the tool path.

allow -> tool_broker -> tool
05

Receipt returns

The resulting status and evidence remain connected to the original request and its authorization decision.

outcome -> receipt -> agent

Contract surface

Small records. Strong boundaries.

The fields below express the concepts that must stay visible as an action moves through Cortex. Implementations may add context, but the decision and writer remain explicit.

Core execution records
Record Required meaning Example values
action_request A proposed operation and target emitted by the agent. read, write, target reference
authorization The kernel's decision under the applicable authority and policy. allowed, denied
writer The mediated component responsible for producing a write effect. tool_broker
status The current state of the request in the execution path. proposed, denied, executing, executed
receipt Evidence connecting request, decision, broker, and outcome. receipt identifier and outcome data

What Cortex is

An execution kernel and authorization boundary around tool-using agents. Its purpose is to make actions governable and accountable.

What Cortex is not

It is not a smarter agent. It does not replace reasoning or invent authority. It governs the path from an agent's proposal to an allowed, recorded effect.

Receipt shape

Evidence that can travel with the action.

A receipt is the compact record of what Cortex knows about an execution. It is designed to be read by operators and systems after the originating model has continued its work.
