Cortex

A checkpoint between an AI that writes code and the code that actually ships.

An AI assistant can suggest changes to software. Cortex is designed so it cannot make one on its own. Whether that holds across every route is still being verified, and this deck says which parts are proven.

  • 01The AI proposes; a separate program writes.
  • 02A change should not reach the real code without a human approving that exact change.
  • 03Each approval is a permit for one change, spent on use.

Those are the design's intentions. Slide 7 states which are demonstrated, which are unverified, and which have been refuted. It is not in production and is not a sole security boundary.

The problem

Giving an AI the keys is the easy part. Getting them back is not.

An AI coding tool is often handed the same access a developer has: edit files, commit, push. When it works, it is fast. When it goes wrong, there is frequently no record of what changed, who allowed it, or whether anyone did.

The honest comparison is not against an unrestricted agent. A serious conventional setup already uses ephemeral sandboxes, scoped tokens or GitHub Apps, protected branches, CODEOWNERS, required CI and a policy engine such as OPA or Cedar. Much of what Cortex does, that stack also does.

The open question is whether binding an approval to exact content, and recording evidence per effect, catches failures that stack misses. That benchmark has not been run. Until it is, treat the case for Cortex as unproven rather than established.

How it works

Five steps, and a refusal available at every one.

If a step refuses, the write does not happen. That is fail-closed authorisation, which is not the same as transactional rollback: temporary files, worktree state or side effects from earlier steps can survive a refusal.

1 The AI proposes a changeIt has no keys and cannot write anything Proposed
2 Is this allowed at all?Scope, files, permissions. Anything unclear is refused Can refuse
3 You approve the exact changeA permit is issued, tied to that change, valid once Can refuse
4 Is it still the same change?Re-checked at the last moment, right before writing Can refuse
5 The broker writes it, and records a receiptThe intended sole writer. What, when, approved by whom Done

This diagram assumes the broker is the only route to an effect. That assumption is not yet proven: a builder refused through the editing tool has been observed performing the same write through a shell, and the current guard is a speed bump rather than a boundary. Enumerating every effect route, and showing the check sits on all of them, is outstanding work.

The central idea

The permit is the central binding mechanism.

An approval is not "yes, go ahead". It is a permit bound to one specific change, valid once. Change a single character afterwards and the permit no longer matches, so the write is refused.

It is not the whole trick. It depends on the broker actually being isolated, on consumption being atomic under concurrency, on the fingerprint covering the right canonical representation, and on every effect route reaching the check. A permit offers nothing against a compromised broker, a stolen credential, or an approver who was shown a misleading diff.

Why it may deserve evaluation

Six answers, and what each is actually worth.

Most of the right-hand column describes what the design does, which is not the same as evidence that it cannot be bypassed. Read it as a claim set to be tested, not as assurance.

What worries peopleWhat Cortex does about it
"The AI could do something I didn't ask for." The AI holds no keys. A separate, ordinary program does all writing, and only accepts changes carrying a valid permit.
"What if something slips through?" Everything is refused unless explicitly allowed. No path where silence or an error means "go ahead".
"How do I know what was approved is what was done?" The permit is tied to a fingerprint of the exact change, re-checked at the last moment before writing.
"Could it reuse an old approval?" Permits work once and are spent on use. A used permit is refused.
"You wrote the tests, so of course they pass." It is judged against reference-monitor criteria published in 1972, which nobody here wrote and nobody here can edit. Judged against, not yet passing: one of the six is currently refuted.
"Every project claims it's secure." This one publishes what is not working. That is a disclosure practice, not a security property, and a documented weakness is still a weakness.

Honest status

What is proven, and what is not.

Being able to say this precisely is the point of the project, so it sits beside the claims rather than behind them.

Holds, in test

The permit check refuses bad permits

Forged, replayed, spent and wrong-subject permits were all refused under cross-model attack. Scope: the permit-verification path. It does not establish that every write route reaches that check.

Holds, one site

Approvals are bound to exact content

Fixed and verified this week at the composition apply site: content is re-derived and compared immediately before the write. Not yet at the pull site, where the verifying function is not called at all.

Refuted

The checkpoint cannot be tampered with

Not merely unverified. Five defects were reproduced this week: custody of a receipt can be transferred, erased, or bound to a run that never existed, while the integrity checks still report success. The affected subsystem is not yet wired into the live path, so the defects are latent rather than exploitable today. Tamper resistance is foundational to the reference-monitor claim, so this is the most important line on the page.

Not yet

Running in production

The control layer is being verified end to end. The parts that execute work in an isolated container are still outstanding.

The finding that matters

Three AI models from different companies, never shown the tests, raised 11 findings a fully passing test suite had missed.

10 are distinct: 6 code defects and 4 contract ambiguities. Each was reproduced with a script before being believed. One is fixed so far, and it is the only one carrying a regression test. Tests passing is not evidence that a system works; building the thing that can tell the difference is what Cortex is for.

The earlier version of this slide said "nine", and an audit of our own evidence could not derive that number: the source document gives three incompatible counts. Two further corrections from the same audit, recorded rather than quietly dropped. The assessors were shown the contract as well as the code, so "only the code" was false. And they were handed a list of attack families, so 7 of the 11 findings map onto a prompted angle: they invented the tests, not the angles. "Different vendors" is also weaker independence than it sounds, since models can share training data and failure modes. This is cross-model adversarial review, not independent verification.
