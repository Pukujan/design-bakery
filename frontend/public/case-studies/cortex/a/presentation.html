Cortex

Let an AI agent do real work, without handing it the keys.

An AI coding agent can propose changes to your software. Cortex is the part that decides what it is actually allowed to do.

  • 01You approve a task once: what it is for, which files it may touch, what finished means.
  • 02Inside that line, the agent works on its own. It does not ask again.
  • 03Anything that would cross the line stops, and asks you first.

Ten slides. Cortex has three parts, at three very different stages of completion, and each slide is stamped with how built that part really is. The last two slides say plainly what is proven, what failed, and what does not exist yet.

The problem

Today, an AI tool usually gets the keys to everything.

The normal way to use an AI coding tool is to point it at your whole project and let it work.

From that moment it can read every file, and it can change anything it can reach. The task may have needed four files; the model got all of them.

When that goes well, it is fast. When it goes wrong, there is often no record of what changed, who allowed it, or whether anyone allowed it at all.

And whatever the model reads can end up inside a prompt, sent to another company's servers. From the outside, you cannot tell reading from sending.

The core idea

Every decision Cortex makes runs on your machine.

The rules, the approvals, the credentials that can write, and the record of everything done: all of it lives and runs locally. None of it is ever held by a vendor.

Said in the same breath, because it matters: the AI model itself is not local. The agent still calls a cloud model to think and to write code. Cortex controls what that agent may do, and aims to control what it may see; it does not move the model onto your machine.

Boundary 1 of 3 · the work boundary Partly built

Approve the task once. The agent works alone inside it.

This is not a person clicking Approve on every change; approving once and then letting it run is the whole point. You say up front what the task is for, which files it may touch, and what counts as finished. Routine work inside that plan goes ahead without asking. Only a change that crosses the line stops.

The measured gap

A change can reach the repository by many routes: the editing tool, the shell, git itself. We count 25 such routes. The check above currently sits on 4 of them; 21 of 25 effect routes still reach the repository without passing the check. That number is measured on every run, and it is the honest status of this boundary.

The diagram also assumes the checkpoint is the only door. Not yet proven: an agent refused by the editing tool has been seen making the same change through the shell. Closing every route is the outstanding work.

Not built

None of the data boundary is built. Today Cortex guards what an agent writes, not what it reads, so nothing currently stops it putting a file into a prompt. This is exactly why the caveat on slide 3 is said in the same breath as the claim.

Boundary 3 of 3 · the assurance system The most built part

Testing whether the boundaries are real.

A safety control can look perfect on paper and be connected to nothing. It passes every human review, and it does nothing. So the most built part of Cortex is the machinery that tests its own boundaries, three ways at once.

Think of checking a locked building: rattle the doors from outside, watch the alarms while someone tries to get in, then open the wall and inspect the wiring. Passing one of the three is not passing.

HowWhat it asksWhat only it catches
From outside
the doors		 Act like an agent and try to get past the boundary: reach a file that is off limits, write by an unexpected route, reuse a spent permit. Failures nobody thought to write a test for. This is how the finding on the last slide was made.
From inside
the alarms		 Watch a real task run: which checks fired, what was sent out, whether every write went through the checkpoint. A check that exists but sits on the wrong path, so a real task never touches it. One component was invoked zero times during a complete run.
At the code
the wiring		 Read the code itself: routes around the checkpoint, defaults that allow when they should refuse, checks that cannot fail. That the main permission check was not connected to any running program. It existed, and nothing called it. Found by reading, not by testing.

A fair comparison

Against a good conventional setup, Cortex lost 5 of 9 rows.

The honest comparison is not with an agent that has no rules. A careful team already uses scoped access tokens, protected branches, and required human review. We scored Cortex against that setup, row by row, and Cortex lost 5 of the 9 rows.

rows lost to the conventional setup (5)the remaining rows (4)

What that conventional stack does not cover: what the model gets to see (the unbuilt boundary on slide 5), and a receipt tied to each individual change. Whether those two catch real failures the stack misses is the open question, and that benchmark has not been run. Until it has, treat the case for Cortex as unproven rather than established.

Honest status

What holds, what failed, what is not there.

Being able to say this precisely is the point of the project, so it sits beside the claims, not behind them.

Holds, in test

The permit check refuses bad permits

Forged, replayed, already-spent, and wrong-owner permits were all refused when three outside models tried to slip them through. Scope: the permit check itself. It does not show that every write route reaches that check; slide 4 says most do not yet.

Holds, one site of two

Approvals are bound to exact content

Changes land in two places. At the first, this was fixed and verified this week: the content is re-derived and compared immediately before writing. At the second, the checking function is never called at all. Fixed in one place is not fixed.

Refuted

The record-keeping cannot be tampered with

Not merely unverified: shown false. Five defects were reproduced this week. A receipt's ownership can be transferred, erased, or tied to a run that never happened, while the integrity checks still report success. The affected part is not yet wired into the live path, so the defects are latent rather than live. Tamper resistance is foundational here, which makes this the most important line on the page.

Not in production

Nobody should run this in production today

The control layer is still being verified end to end, and the part that runs the work inside an isolated container is still outstanding. That includes us.

The finding that matters

Three AI models from other companies, shown the code and the contract but never the tests, raised 11 findings a fully passing test suite had missed.

Of the 11, 10 are distinct: 6 defects in the code and 4 ambiguities in the contract. Each was reproduced with a script before being believed. One is fixed so far, and it is the only one carrying a regression test.

A green test suite is not evidence that a system works; it is evidence that the system passes the tests someone thought to write. Building the thing that can tell the difference is what Cortex is for.

Corrections, kept in view

An earlier version of this slide said "nine findings"; our own audit could not derive that number from its source, so it was withdrawn. An earlier version also said the models saw "only the code"; they saw the contract too. They were handed a list of failure families to probe, so 7 of the 11 findings follow a prompted angle: they invented the tests, not the angles. And models from different companies can share training data and blind spots, so this is cross-model review, not independent verification.
